# Codex wire contract

This document defines what cliproxy-rs must send and deliver on Codex routes. The
first-party Codex client and OpenAI's published documentation define the contract.
CLIProxyAPI's Go code does not. The document covers each endpoint profile and transport
separately, lists every permitted change to a payload, and marks missing evidence as
unknown.

Tracker: [#20](https://github.com/zakstak/cliproxy-rs/issues/20). This document is the
deliverable of [#21](https://github.com/zakstak/cliproxy-rs/issues/21). It describes the
target contract. The proxy at `c610d7d8` does not meet it yet. [Known deviations at the
baseline](#known-deviations-at-the-baseline) lists where it differs, and which issue owns
each fix.

## Sources of authority

The contract rests on two sources, in this order:

1. First-party Codex at [`openai/codex@44ccf394573c`](https://github.com/openai/codex/tree/44ccf394573cabb95e1f751a59f9d76f6f79faf1),
   mainly `codex-rs/codex-api/src/common.rs`, `codex-rs/core/src/client.rs`,
   `codex-rs/codex-api/src/endpoint/responses_websocket.rs` and
   `codex-rs/codex-api/src/sse/responses.rs`. Line references in this document point at
   that commit.
2. OpenAI API documentation: the
   [WebSocket mode guide](https://developers.openai.com/api/docs/guides/websocket-mode),
   the [mid-turn steering guide](https://developers.openai.com/api/docs/guides/steering),
   the [prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
   and the [`POST /responses/compact` reference](https://developers.openai.com/api/reference/resources/responses/methods/compact).
   These pages were read on 2026-11-07. They describe the OpenAI API. They say nothing
   about the ChatGPT Codex backend.

The following rules decide how to use the sources:

- A field in a first-party type shows that the client can send it. It does not show
  that every endpoint accepts it. Each claim below names the endpoint profiles its
  evidence covers.
- When neither source covers an endpoint, the entry says "unknown". Unknown is not
  "unsupported". A later PR may not fill an unknown with Go behaviour.
- Go v8.0.35 recordings (`crates/cpa-exec/tests/fixtures/codex_go*.json` and the other
  `*_go.json` Codex files) stay labelled with their original versions. They are
  historical regression evidence for behaviour not yet migrated. They never define the
  Codex contract.
- Fixtures are never generated by running this proxy. See
  [Contract fixtures and test helpers](#contract-fixtures-and-test-helpers).

Other providers keep the Go v8.0.35 parity rule in [AGENTS.md](../../AGENTS.md).

## Endpoint profiles

A Codex credential resolves to one of four endpoint profiles.
`crates/cpa-exec/src/codex_request.rs` `View::new` picks the profile from the credential.

| Profile | Base URL | Upstream credential | First-party evidence |
| --- | --- | --- | --- |
| `chatgpt` | `https://chatgpt.com/backend-api/codex` | ChatGPT OAuth access token as `Authorization: Bearer`, plus `chatgpt-account-id` | `model-provider-info/src/lib.rs:472-487` selects this base URL for ChatGPT, agent-identity and personal-access-token auth. `model-provider/src/auth.rs:166-190` adds `chatgpt-account-id`. |
| `api-key` | `https://api.openai.com/v1` | OpenAI API key as `Authorization: Bearer` | `model-provider-info/src/lib.rs:484` selects this base URL for API-key auth. The OpenAI API documentation applies. |
| `siwc` | `https://api.openai.com/v1`, unless the credential sets `base_url` | The credential's Sign in with ChatGPT access token (`siwc.access_token`, scope `chatgpt.tokens.use.direct`) as `Authorization: Bearer` | None for Responses. The pinned client mentions SIWC only in realtime code (`codex-api/src/endpoint/realtime_call.rs:146`, `core/src/realtime_conversation.rs:2092`). Every Responses behaviour on this profile is unknown, so the proxy adds nothing: the profile takes the native and translated routes with only the permitted transformations (#28). |
| `compatible` | An operator-set `base_url` on any other host | Whatever the credential holds | None. Only explicit routing applies. Every behaviour beyond routing is unknown. |

The first-party built-in OpenAI provider sets `supports_websockets: true`
(`model-provider-info/src/lib.rs:609`) for both the `chatgpt` and `api-key` base URLs.

## Transport matrix

The key for the matrix:

- **FP**: the pinned first-party client does this on this profile.
- **Docs**: OpenAI API documentation describes it.
- **Unknown**: neither source covers it.
- **Not used**: the pinned client never does it.

| Behaviour | `chatgpt` | `api-key` | `siwc` | `compatible` |
| --- | --- | --- | --- | --- |
| HTTP `POST /responses`, streaming SSE | FP | FP, Docs | Unknown | Unknown |
| HTTP `POST /responses` with `stream: false` | Not used, acceptance unknown | Docs | Unknown | Unknown |
| Responses Lite (`x-openai-internal-codex-responses-lite: true`) | FP, when the model catalog sets `use_responses_lite` | Unknown | Unknown | Unknown |
| Remote compaction v2: `POST /responses` ending in a `compaction_trigger` item | FP | FP | Unknown | Unknown |
| `POST /responses/compact` | Not used, acceptance unknown | Docs (not used by the pinned client) | Unknown | Unknown |
| WebSocket `response.create`, first turn | FP | FP, Docs | Unknown | Unknown |
| WebSocket continuation with `previous_response_id` | FP | FP, Docs | Unknown | Unknown |
| WebSocket prewarm, `generate: false` | FP | FP, Docs | Unknown | Unknown |
| WebSocket `response.interrupt` | FP | FP, not in Docs | Unknown | Unknown |
| WebSocket `response.steer` | Not used, acceptance unknown | Docs, GPT-6 family only. Not used by the pinned client. | Unknown | Unknown |
| WebSocket `response.append` | Not used, acceptance unknown | Not used, not in Docs | Unknown | Unknown |
| WebSocket `stream_id` lanes | Not used, acceptance unknown | Docs. Not used by the pinned client. | Unknown | Unknown |
| HTTP fallback after a `426 Upgrade Required` handshake | FP | FP | Unknown | Unknown |
| Request body `zstd` compression | FP, when the client enables request compression | Not used | Unknown | Unknown |

The first-party sources for each row:

- HTTP streaming: `codex-api/src/endpoint/responses.rs:123-158` posts to `/responses`
  with `Accept: text/event-stream`. `core/src/client.rs:1162-1316` builds the body.
- Responses Lite: `core/src/client.rs:1198-1213` moves the tools into a leading
  `additional_tools` input item and sends no top-level `tools`. Line 1300 forces
  `parallel_tool_calls: false`. Lines 2701-2707 add the header.
- Compaction v2: `core/src/compact_remote_v2_attempt.rs:228` appends
  `{"type":"compaction_trigger"}`. `core/src/compact_remote_v2.rs:291-384` sends the
  request through the ordinary Responses stream, and lines 386-492 require exactly one
  `compaction` output item before `response.completed`. The pinned repository contains
  no reference to `/responses/compact`.
- WebSocket first turn and continuation: `codex-api/src/common.rs:341-403` defines the
  frame. `core/src/client.rs:1675-1706` sends a continuation only when every non-input
  field equals the previous request and the new input extends the previous input plus
  the previous output. Lines 2354-2376 then send `previous_response_id` with only the
  new items.
- Prewarm: `core/src/client.rs:2375` sets `generate: false`, and lines 2517-2566 wait
  for `response.completed` before the first real turn.
- Interrupt: `codex-api/src/endpoint/responses_websocket.rs:824-839` sends
  `{"type":"response.interrupt","response_id":...,"mode":"discard_partial_items"}` after
  `response.created`. Lines 886-913 validate `response.interrupt.accepted` and
  `response.interrupt.failed` only for a cancel. A drain, which the client uses for
  steering, keeps reading until the terminal event (lines 310-325).
- HTTP fallback: `core/src/client.rs:1797-1804` and 2266-2272 switch the session to HTTP
  when the upgrade answers 426.
- Request compression: `core/src/client.rs:1932-1940` uses `zstd` only for a
  Codex-backend credential on the OpenAI provider.

"Steering" names two different things. The first-party client steers by sending a
drain interrupt and then a new `response.create`. The OpenAI API's `response.steer`
event is a separate, documented feature for the GPT-6 family. The proxy's
`codex.response-steering` setting comes from Go. It keeps the upstream socket open after
the first response and forwards each later client frame unchanged, so it changes the
transport, not a payload, and it stays. Go's `response.append` frame has no first-party
or documented source on any profile, so it is refused (#28,
[Native WebSocket route](#native-websocket-route)).

## Permitted transformations

A Codex route may change a payload only as this table allows. Every entry names its
reason: a provider requirement, an explicit routing choice by the operator or caller,
a transport envelope, or a cross-API purpose. Anything absent from this table is a
discretionary mutation, and a migrated route must not perform it.

| Transformation | Applies to | Reason |
| --- | --- | --- |
| Replace the client's `Authorization` with the selected credential's token, and set `chatgpt-account-id` from that credential on `chatgpt` | All profiles | Provider requirement. The client's key authenticates to the proxy only and never travels upstream. |
| Map the client path (`/v1/responses`, `/backend-api/codex/responses` and their `/compact` forms) to the profile's base URL plus `/responses` or `/responses/compact` | All profiles | Explicit routing choice. |
| Replace `model` with the upstream model of an operator-configured alias or a caller-selected route, or add it as the first member when the body has none | All profiles | Explicit routing choice. Only the `model` value changes. |
| Wrap an HTTP Responses body in a `response.create` frame by adding `"type":"response.create"` | A credential with `websockets: true` that serves an HTTP client over a WebSocket | Transport envelope. No other field changes. |
| Send a WebSocket `response.create` frame as an HTTP Responses body by removing its `type` member, and send `stream: true` when the frame omits `stream` or sets it to `false` | A credential without `websockets` that serves a Responses WebSocket turn ([WebSocket HTTP fallback](#websocket-http-fallback)) | Transport envelope and adaptation. The first-party frame is the HTTP request plus its tag (`codex-api/src/common.rs:315-339`, 400-406). A WebSocket turn always delivers its response as events, so the HTTP request asks for them; the client receives the upstream's events, never an aggregate. No other field changes; a continuation or prewarm is refused instead. |
| Hand a WebSocket client each event's `data` payload as one text frame | A WebSocket turn served over HTTP | Transport framing. A WebSocket text frame carries one event; the bytes of each payload are unchanged. |
| Send `stream: true` upstream for a buffered client, then build the client's response from the upstream `response.completed` object | `chatgpt`, while `stream: false` acceptance stays unknown | Transport adaptation. The aggregate carries the provider's response object, usage and errors. It does not authorize changes to streamed events. On `api-key`, forward `stream: false` unchanged. |
| Decode the client's `Content-Encoding` to read routing fields | All profiles | Transport. Forward the original bytes, or the decoded bytes when re-encoding is not possible. Never re-serialize the JSON. |
| Convert Chat Completions or Claude Messages requests into Responses, and the responses back | Registered cross-API routes into Codex | Cross-API purpose. [Translated route](#translated-route) lists each retained conversion and its evidence. A conversion that cannot keep the caller's meaning fails with an error before the upstream send. |
| Redact credentials in captured request logs | The capture sink in `crates/cpa-server/src/request_logging.rs` | Credential safety. Redaction changes logs only, never forwarded bytes. |
| Deliver the backend's status-less context-window `error` event to a Codex client as `response.failed` | `chatgpt`, a Codex client (#5) | First-party classification: the pinned client ignores the `error` event (`sse/responses.rs:375-385`) and compacts only on `response.failed` with `context_length_exceeded`. `response.error` is the upstream `error` object byte for byte. |
| Answer a client's `response.interrupt` that no upstream socket can take with a local `response.interrupt.accepted`, and, when it stops a running turn, a local interrupted `response.incomplete` | A WebSocket turn served over HTTP ([WebSocket HTTP fallback](#websocket-http-fallback)) (#1) | First-party cancel handshake. After a cancel, the pinned client waits for both events before its deadline (`responses_websocket.rs:310-333`, 824-839, 886-913). The proxy stops that response itself by cancelling the HTTP request. Both events are local transport answers, not provider output: see the fallback section for their content. |
| Write an SSE comment (`: keep-alive`) while a stream is idle | Streams with `requests.streaming.keepalive-seconds` | Transport framing. Clients ignore comments; no event changes. |
| Send a WebSocket ping control frame to the client while a turn is idle | Responses WebSockets with `requests.streaming.keepalive-seconds` | Transport framing. A ping is not a request: nothing reaches the upstream. |
| Deliver `x-codex-turn-state` and `openai-model` from the upstream handshake as `{"type":"response.metadata","headers":{...}}` before the first event of the turn that opened the socket. Before the first event of each later request on that socket, deliver the socket's `openai-model` alone in the same event shape | Native WebSocket turns (#3, #24) | Transport adaptation. The proxy's own 101 precedes credential selection, and the pinned client reads both headers from this event (`sse/responses.rs:193-222`). A directly connected client re-emits its upgrade model on every request (`responses_websocket.rs:302-303`); turn state stays with the turn that opened the socket. For each request, `openai-model` is left out when the routed model differs from the client's, ignoring ASCII case only, or, as an additional proxy policy, when the socket was opened for another upstream model. Backend applicability after a model switch is unknown. No other header travels. [Handshake metadata](#handshake-metadata) has the rules. |
| Add the line endings that close a final event the upstream left open | Native streams | Transport framing. Without them an SSE client drops that event at the end of the stream. The event's bytes are unchanged. |

No row replaces a provider's `response.incomplete` on a native route. Every one
reaches the client as received, whatever its reason (absent, `null`, empty, unknown or
named), output or usage, and however much of the response was delivered before it
(#25, #7). The earlier row that answered a zero-output end without an exempt reason
with a request-scoped 502, Go's `IsCodexTerminalEmptyIncomplete`, is removed. No
first-party or provider source shows that the backend sends that shape as a silent
abort. The pinned client classifies the event itself
(`codex-api/src/sse/responses.rs:451-506`): `interrupted` ends the turn with
`end_turn: false`, `content_filter` is its own error, and any other reason, `unknown`
when missing or not a string, is a terminal `ResponseIncomplete` carrying the reason,
response ID, usage and incomplete output items. That error has no retry delay
(`protocol/src/error.rs:428-442`), so the client neither retries it nor reads it as a
success. A replacement 502 would drop the ID, usage and partial output and change that
classification. A stream that ends without any terminal event is a different case and
still fails ([Native HTTP route](#native-http-route), [Native WebSocket
route](#native-websocket-route)). The translated route keeps Go's rule until #27
([Translated route](#translated-route)).

[#26](https://github.com/zakstak/cliproxy-rs/issues/26) defines the header policy.
Until it lands, header behaviour stays as it is; see
[Identity and headers](#identity-and-headers).

## Field preservation

On a native route, every byte of a valid caller body reaches the upstream unless a
row of [Permitted transformations](#permitted-transformations) changes it. The rules
below spell out what that means for the fields Codex sends.

- `instructions` and leading developer messages. The pinned client sends base
  instructions as a leading developer `message` with a stable `msg_` ID
  (`core/src/client.rs:1214-1224`). The proxy adds no instructions and removes none.
- `tools`, tool names, namespaces and schemas. The proxy forwards them unchanged,
  including `namespace` on `function_call` items (`protocol/src/models.rs:1141-1166`) and
  `additional_tools` items under Responses Lite. It adds, renames and reorders no tool.
- `parallel_tool_calls`. The pinned client always sends it as an explicit boolean
  (`common.rs:298`). `false` stays `false`, and an absent field stays absent.
- `service_tier`. The pinned client omits it for the default tier and otherwise sends
  the catalog value (`protocol/src/openai_models.rs:1144-1149`), including `flex`. The
  proxy forwards any value, and it never adds or deletes the field.
- `prompt_cache_key` and `prompt_cache_options`. The pinned client sends
  `prompt_cache_options: {"ttl":"30m"}` or `{"ttl":"12h"}`
  (`protocol/src/turn_input.rs:221-228`). The OpenAI API documents `mode`, `ttl` and
  `prewarm` for GPT-5.6 and later, and `prompt_cache_retention` for earlier models. The
  proxy never synthesizes a cache key or cache options, and it deletes none.
  `chatgpt` support for each option is unknown and is the upstream's to reject.
- `include`, `store`, `reasoning`, `text`, `stream_options`, `client_metadata` and
  `access_programs`. The proxy forwards them as sent. `reasoning` is the one
  non-skipped `Option` in `ResponsesApiRequest` (`common.rs:299`), so `"reasoning":null`
  is a valid first-party spelling.
- Omission, `null` and `false` are three different values. The proxy preserves
  whichever the caller sent.
- Unknown members, at any depth, and unknown item kinds. The first-party decoder keeps
  unknown item kinds as `ResponseItem::Other` (`protocol/src/models.rs:1339-1340`). The
  proxy forwards both.
- Opaque IDs and encrypted content. `id`, `call_id`, `previous_response_id`,
  `encrypted_content`, `encrypted_function_args` and `compaction` items are opaque. The
  pinned client already strips IDs that lack a prefix (`core/src/client.rs:1318-1327`)
  and clears encrypted content for non-OpenAI providers (lines 1231-1250). These are
  client decisions. The proxy repeats neither of them.
- Raw JSON spelling. Number spelling, string escapes and key order survive inspection.
  [Request boundary](#request-boundary) defines malformed input, duplicate keys and
  size limits.

## Request boundary

`cpa_common::codex_body::CodexBody::parse` is the one parser for Codex request bodies
([#22](https://github.com/zakstak/cliproxy-rs/issues/22)). It lives in `cpa-common` so
that executor, server and translator code all reach the same policy. It reads the body
once, in place, and returns the top-level members as slices of the caller's bytes. It
never copies the body, never builds a value tree and never re-serializes. It checks
numbers against the JSON grammar without converting them, so `1e400` and a 40-digit
integer pass with their spelling.

The boundary refuses a body for the following reasons, with these client-facing errors:

| Rule | Status | Message |
| --- | --- | --- |
| Larger than 64 MiB, the server's request limit (see below for the route) | 413 | `request body exceeds 67108864 bytes` |
| Not UTF-8 | 400 | `request body is not valid UTF-8 at byte N` |
| Not RFC 8259 JSON, including content after the root value, a control character in a string, and a lone or mismatched surrogate escape | 400 | `request body is not valid JSON at byte N` |
| A key repeated in any object, compared after unescaping | 400 | `request body repeats an object key at byte N` |
| Arrays and objects nested more than 100 levels deep, counting the root object | 400 | `request body nests deeper than 100 levels at byte N` |
| A root that is not an object | 400 | `request body must be a JSON object` |
| `model` not a string, `stream` not a boolean, or `previous_response_id` neither a string nor null | 400 | ``request field `model` must be a string``, and the same for the other two |

Every refusal is a request fault (`FailureScope::Request`), so it never fails over to
another credential. Messages name byte offsets and protocol fields only, never body
content. Any other member, at any depth, passes as long as it is valid JSON.

The size row is the boundary's own limit. Through the server, a body never reaches it:
the server reads every client request under the shared 64 MiB limit
(`cpa_server::MAX_REQUEST_BYTES`, the same number) before it knows the provider, and a
WebSocket message under the same limit. A larger HTTP body gets the server's answer for
every provider: 400 with `Invalid request: Failed to buffer the request body: length limit
exceeded`, or 413 with `http: request body too large` under a smaller
`server.max-request-body-bytes`
([Request body limits](../DIFFERENCES-FROM-GO.md)). Both are client-safe and come before
any upstream send. The boundary's 413 applies to a caller of the executor that skips the
server. Mapping the server's limit to 413 would change the shared limit for every
provider, so it is not done here.

The Codex executor applies the boundary at its entry points, `CodexExecutor::execute`
and `CodexExecutor::execute_in_session`, to every body whose source and response formats
are both Responses: HTTP streaming, buffered, compact and WebSocket turns, and a local
token count. A refused body fails there, before translation and before any upstream send. A body that passes goes
upstream unchanged except for the permitted transformations: every Responses request
takes a native route (#28). A native WebSocket connection also reads each later client frame through the
boundary. The
boundary does not judge bodies from other client formats, which reach Codex through a
cross-API translator (#27).

The Images API adapter reads a client's JSON body through the same rules
(`CodexBody::parse_object`), on the direct and the tool path, before anything is sent.
The Responses member types do not apply to an Images body. The adapter types each member
it reads instead: `model`, `prompt`, `response_format` and the image settings are strings,
`stream` is a boolean, `n`, `output_compression` and `partial_images` are numbers, and an
image or mask reference holds string `image_url` or `file_id` members. `null` reads as
absent. A member of another type is refused with the same 400 message, for example
``request field `size` must be a string``. Nothing is coerced, and the tool request copies
a count with its number spelling. The tool path expresses `n` only as one image, and
compares it with one by its decimal digits: `1`, `1.0` and `1e0` are one, and
`1.0000000000000001`, which a float rounds to one, is refused as an `n` the tool cannot
express. The boundary does not apply to the Responses body that the tool path generates.

The shared Images handler (`cpa_server::images`) rewrites `model` and `stream` before the
adapter sees the request. For a model Codex serves, it first applies the adapter's rules
to the client's original bytes (`cpa_exec::codex_images::check_json` and `form_routing`),
so its rewrite cannot erase a fault: `{"stream":false,"stream":true}` is refused, in
either order, rather than reaching the adapter with one `stream` left. xAI models keep
Go's ingress, and a repeated `model` cannot move a request between providers: Go's first
`model` picks xAI, and a first Codex `model` meets these rules before any credential is
chosen.

A multipart edit has no JSON types, so the form rules are these, on both paths:

| Form text | Rule |
| --- | --- |
| Any text field | Must be UTF-8: ``request form field `prompt` is not valid UTF-8 at byte N`` |
| `model`, `stream` | Must not repeat (``request form field `stream` is repeated``), because each decides where the request goes or how it is answered |
| `stream` | One of `true`, `1`, `yes`, `on`, `false`, `0`, `no`, `off` (Go's `parseBoolField` spellings), ASCII white space trimmed and ASCII case ignored; empty is false, as an unset field. Anything else gets ``request form field `stream` must be a boolean``; Go reads it as false |
| Other fields, tool path | Must not repeat: the tool reads one value |
| `output_compression`, `partial_images`, tool path | A decimal `i64` (optional sign, digits) after trimming, or ``request form field `partial_images` must be an integer``. The tool has no other spelling for it, and leaving it out would request the provider's default instead of the client's value |
| `n`, tool path | A JSON number spelling, optionally with a leading `+`, exactly equal to one; otherwise the `n` conversion refusal |
| Count fields, direct path | Text that is a decimal `i64` becomes that JSON integer; other text stays a JSON string, so the Images endpoint judges the value the client sent. Other repeated fields become JSON arrays, as in Go |

Field names are literal, without trimming or case folding. A padded count name stays an
unknown string field, not a recognized numeric control, and its text still must be UTF-8.
The shared multipart decoder ignores parts with an empty name; a whitespace-only name
is still a field name and is preserved on the direct path.

Image and mask files are binary and are never read as text. The OpenAI Images API documents
`n`, `output_compression` and `partial_images` as integers and `stream` as a boolean.
Whether the ChatGPT backend, or a Sign in with ChatGPT credential's tool path, accepts a
given value is unknown; the proxy refuses only what it cannot represent.

The shared ingress parser `cpa_server::claude::peek` reads `model` and `stream` for
every provider before a credential is chosen. It keeps its Go behaviour: it already fails
on trailing content and on a repeated top-level `model` or `stream`, and such a body
never reaches the Codex boundary.

### Remaining Go JSON callers on the Codex path

The native HTTP and WebSocket routes use the boundary for request routing and edits;
header observation borrows raw fields without changing the body.
#28 deleted the last request rewrites (`shape` and its helpers, the payload finalizer,
the Sign in with ChatGPT body rules and the Codex executor's multi-agent optimization),
so no Codex request path edits a body through the Go helpers. The callers below read,
or rewrite only for other providers. They read through `crates/cpa-common/src/json.rs`, the
Go-compatible port, directly or through its `&str` facade `cpa_common::rawjson`; the
third-party Rust gjson crate and its vendored copy are removed.
[The migration record](../GJSON-MIGRATION.md) lists the reader of each surface and the
reader semantics.

## Native HTTP route

[#23](https://github.com/zakstak/cliproxy-rs/issues/23) and the HTTP half of
[#25](https://github.com/zakstak/cliproxy-rs/issues/25) put the following route in place.
A request takes it when all of these hold:

- it arrives on `/v1/responses`, `/backend-api/codex/responses` or their `/compact` forms;
- the selected credential is a Codex credential served by the built-in executor, on any
  profile (`chatgpt`, `api-key`, `siwc` or `compatible`);
- both the client and response formats are Responses, and the request is a generation.

WebSocket turns take the [native WebSocket route](#native-websocket-route), and
translated requests take the [translated route](#translated-route). A request that
neither route carries (another source format, or a compaction from a client that is not
a Responses client) is refused with a 400 before any upstream request; no legacy rewrite
stands in (#28). A client Responses request that a built-in Codex credential cannot
carry natively is refused the same way, so the request other providers receive after the
ingress rewrites never reaches Codex.

The request goes upstream as the client sent it, with only the permitted
transformations: the routed `model`, and `stream: true` for a buffered client on
`chatgpt`. The server keeps the client's body, headers and route path in
`dispatch::NativeRequest`, from before the Codex-client ingress rewrite and compact's
`stream` deletion, so a native attempt never sees their output.

A native attempt is possible when the selectable credentials for the model include a
built-in Codex credential on a native profile. Under Home the pool is remote and unknown,
so every Responses HTTP request counts. The session, session affinity, the LCP prefix,
Home dispatch headers and the executor's session metadata then come from the client's
own request (`Call::selection_inputs`). When a native attempt is not possible (a model
only other providers serve), selection reads the rewritten request, as in Go. Sign in with
ChatGPT credentials are native too (#28). No translation, thinking suffix, payload rule, prompt-cache
key, reasoning replay, or tool or namespace preparation runs on a native attempt. A model
with a thinking suffix, such as `gpt-5.5(high)`, is refused with a 400, because the
suffix would need a body change the contract does not permit.

There are no plugin hooks to bypass: native plugins are removed (#47), and a config with a
`plugins` section is refused ([Settings](#settings)).

The response reaches the client as the upstream sent it:

- A stream's events are forwarded byte for byte, unknown and private events included,
  with no event renamed, no output repaired and no usage added. Usage, capture and
  failure classification read a copy. The observer splits lines as the shared SSE
  framer does (`\r\n`, `\r` or `\n`) and joins a multiline `data` field in one pass.
- A request that was sent is never sent to another credential once the upstream may
  have read it (N1 #111): a lost connection after the request left, and a broken body
  after a success status, are request-scoped failures, whether or not
  `stream-bootstrap-buffering` still holds `response.created`. Only a connection that
  could not be made (DNS, TCP, TLS or proxy setup) or a request whose deadline passed
  before it was sent fails over; an explicit upstream rejection keeps its failover.
- Leading handshake events are held under `stream-bootstrap-buffering`, using their
  decoded classification view; positional and object envelopes are held alike. The held
  events are `response.created`, `response.in_progress`, `codex.rate_limits`,
  `codex.response.metadata`, `response.metadata`, keepalives and empty output items:
  the pinned reader takes no response content from `response.metadata`, only headers,
  turn state and notices (`sse/responses.rs:213-290`, 545). A serving attempt releases
  them unchanged and in order; a failed attempt's held events never reach the client
  (N1 #111). A failure that
  arrives before anything was delivered fails over to another credential when its scope
  allows it; otherwise the provider's event is delivered. After something was delivered,
  a failure ends the stream after its event and is never replayed on another credential.
- Every `response.incomplete` is a terminal event and reaches the client as received, at
  any stage, including as the first event and after events held for bootstrap.
  [Permitted transformations](#permitted-transformations) explains why nothing replaces
  it.
- A stream that ends without a terminal event ends for the client too, without a local
  event. The proxy invents neither a `response.incomplete` nor a completion for it. The
  attempt records a request-scoped 408. A final event the upstream left open gets the
  line endings that close it.
- The observer reads upstream events as the pinned client decodes them, not through the
  client [request boundary](#request-boundary). The pinned client decodes each event
  into `ResponsesStreamEvent` and skips an event that does not decode
  (`sse/responses.rs:161-179`, 633-643). An event decodes when it is one JSON value
  whose known members (`type`, `headers`, `metadata`, `response`, `response_id`,
  `error`, `item`, `item_id`, `call_id`, `delta`, `text`, `summary_index`,
  `content_index`, `safety_buffering`) each appear at most once, with the struct's
  types, and whose `type` is a string. Unknown members are ignored, repeated or not.
  A key repeated inside a known member's value is ignored too, and the client's
  `serde_json::Value` keeps the last one. A number of any size counts, because the
  first-party build enables serde_json's `arbitrary_precision` and `raw_value`
  (`exec-server-protocol/Cargo.toml:25`; `Cargo.lock` pins serde_json 1.0.149). With
  them, that `Value` reads an object whose first key is serde_json's private
  `$serde_json::private::Number` or `$serde_json::private::RawValue` token as a number
  or as JSON text, and refuses it unless it has that one member holding exactly one
  JSON number, or JSON text that itself decodes. The token is an ordinary key anywhere
  else, and in unknown members. `crates/cpa-exec/src/codex_event.rs` makes the same
  decision with the same serde-derived shape and a one-pass check of each known
  `Value` member for nesting, surrogate escapes and those tokens; the proxy's own
  serde_json features stay unchanged. Only a decoded event ends the response, fails
  it, is converted (#5) or feeds usage. An event that does not decode, such as invalid
  JSON, a repeated `type` or `response`, a known member of the wrong type, or an
  invalid private token, passes as sent. It counts as delivered content, and the
  stream goes on to the next event.
- A decoded event ends the response only where the pinned reader of the client ends it
  (`process_responses_event`, `sse/responses.rs:375-562`, and its callers). Both
  readers end on a `response` that reads as `ResponseCompleted` (lines 109-159: a
  string `id`, and a `usage`, `usage_metadata` and `end_turn` of their types or
  absent) on a `response.completed` or an interrupted `response.incomplete`, and on a
  `response.incomplete` with any other reason but `content_filter`, which is a
  `ResponseIncomplete` the SSE reader returns at once (lines 680-688). A
  `response.completed` whose `response` is missing or `null` returns no event, and
  `response.done` is not handled, so both pass as sent and the stream goes on; usage
  skips them. The readers part on a processing error: a `response` that does not read
  as `ResponseCompleted`, on a `response.completed` or an interrupted
  `response.incomplete`, and a content-filter `response.incomplete`. The SSE reader
  records it and reads on (lines 677-690); the WebSocket reader returns it, ending the
  turn and retiring its socket (`endpoint/responses_websocket.rs:968-978`, 387-395).
  `crates/cpa-exec/src/codex_event.rs` reads `ResponseCompleted` with the pinned
  struct's shape (positional arrays, missing `Option`s and defaults included), the last
  of a repeated key and the first-party `Value`'s private tokens; a 355-case
  differential against the pinned code built with serde_json 1.0.149 and its features
  matches every outcome.
- Over HTTP the client is an SSE reader, so such an event passes as sent and the
  response goes on. A later terminal event ends it and decides it: a streaming client
  receives every event, a buffered answer is that later event's `response` object, and
  usage is that event's, never the earlier one's. When the upstream ends cleanly
  without one, the response ends on the last such event: the pinned SSE reader then
  reports the error it recorded (lines 616-621), which the client reads from the event
  it has, so nothing is added to the stream. A buffered answer is that event's
  `response` object, and the one record carries its reported usage, not failed. Only a
  clean end does that: a read failure before any terminal event fails the attempt,
  because the pinned SSE reader returns a read error at once (lines 602-614). A
  streaming client gets the read failure after the events, and a buffered client the
  request-scoped 408 of a stream without a terminal event; either record is failed and,
  like every failure record (`PublishFailure`), carries no tokens. A terminal event or
  failure before the read failure still decides the answer. A failure event after it
  ends the response as any failure does. A stream that ends with no
  terminal event and no such event still fails with the request-scoped 408. A
  WebSocket turn served over HTTP is read by a WebSocket client, so it ends on such an
  event, as on an upstream socket ([Native WebSocket route](#native-websocket-route)).
- A failure is classified as the pinned `Value` holds it: each object keeps the last of
  a repeated key, compared after unescaping, and a member value that is serde_json's
  private number or raw value is the number or the JSON text it holds, read the same way
  (`value/de.rs` `visit_map` at serde_json 1.0.149;
  `crates/cpa-exec/src/codex_event.rs` `pinned_view`). That reading decides the status, scope,
  retry hint, usage-limit, capacity and overload checks, the #5 context-window
  conversion and the account-failure boundary. The client still receives the event's
  own bytes; #5's converted event embeds the upstream `error` object as sent.
- An upstream HTTP error keeps its classification for the scheduler, and the client
  receives the upstream's status, body and filtered headers unchanged
  (`ExecError::delivered_status`). The scheduler may classify a usage or capacity limit
  as 429 while the client still gets the upstream's 400 or 503.
- A buffered `chatgpt` answer is the terminal event's `response` object, byte for byte.
  For a `response.incomplete` that is the incomplete response, `status` and
  `incomplete_details` included, under HTTP 200, as the upstream reported it.
  On `api-key` and `compatible`, a JSON answer passes unchanged. Compaction answers pass
  unchanged.
- A failure event the client does not receive as an event (a buffered answer, or a
  failure before anything was delivered that the scheduler fails over) is delivered as
  `{"error":<the provider's error object>,"sequence_number":<as sent>}`, byte for byte
  from the event, or as the whole event when it has no error object or its `response`
  repeats `error`. Nothing is filled in. It arrived on an HTTP 200, so its status is
  the classified one.
- The alias `force-mapping` model rewrite does not run.
- Nothing above delivers an authentication value the request carried
  ([Credential isolation](#credential-isolation)).

[Settings](#settings) lists the final outcome of every Codex rewrite and impersonation
control on every route.

## Native WebSocket route

[#24](https://github.com/zakstak/cliproxy-rs/issues/24) and the WebSocket half of
[#25](https://github.com/zakstak/cliproxy-rs/issues/25) put the following route in place.
A turn of the Responses WebSocket (`GET /v1/responses` and its aliases) takes it when all
of these hold:

- the client frame is a `response.create`: a first turn, a continuation with
  `previous_response_id`, a prewarm with `generate: false`, or a create the client sends
  while a response runs;
- the selected credential is a Codex credential served by the built-in executor, on any
  profile, with `websockets: true`.

A Codex credential without `websockets` serves the turn over HTTP, as described under
[WebSocket HTTP fallback](#websocket-http-fallback). An other-provider credential follows
its own rules, as on HTTP.

Any other client frame bound for a built-in Codex credential is refused with a 400 that
names it, before anything is sent (#28). That covers Go's `response.append`, which no
first-party or documented source defines: Go turned it into a `response.create` with the
parent response and its `instructions` filled in, and shaped it with payload rules. On a
`codex.response-steering` connection the refusal is a local `error` event and the
connection stays open; on an ordinary turn the client receives the error event and the
connection closes. The client continues with a `response.create` and
`previous_response_id`, as the pinned client does.

Every client frame that would reach an upstream is sent under the client key the
connection was opened with (N1 #111). The key is checked when a frame is admitted: each
turn, each later frame of a `codex.response-steering` connection and each
`response.interrupt`. It is checked again at the write itself, after every wait for the
upstream. On an upstream socket that is once the socket is ready to take the frame
(after its lock, its readiness and any earlier frame's flush) and before the frame is
handed over; a revocation after the hand-over cannot recall it. A turn served over HTTP
is checked before each attempt dials, and again once its connection is up (TCP, TLS and
its ALPN choice, any proxy tunnel), before any HTTP byte is written on it. Such an attempt
always dials a connection of its own and never shares a pooled one, over HTTP/2 or
HTTP/1.1, so it cannot wait on, or queue its request headers into, another request's
connection. A refusal sends no HTTP/2 HEADERS or DATA and no HTTP/1.1 request byte; the
TLS handshake has completed by then. The body is checked once more when the HTTP client
takes it. The check re-runs the upgrade's client-key authentication against
the current config. A key removed from `api-keys` stops the next send, and the
connection never acts as another accepted key it also presents. A refused frame reaches
no upstream, and the client gets a 401 `error` event that names no key; at admission the
connection stays open, and a refusal at the write itself ends the turn or the steering
stream with that event. With no client keys configured, access is open, as for a new
connection. Client keys are proxy access control, not a Codex payload rule: the frame
itself is never changed.

### Requests

The frame goes upstream as the client sent it, and only `model` changes: the routed
model replaces the value in place, or is added as the first member when the frame has
none. The server keeps the client's frame, headers and route path in
`dispatch::NativeRequest`. It does this before the transcript normalization
(`websocket_requests::normalize`, and `normalize_passthrough`, which adds
`stream: true`), the multi-agent and orphan-delegation preparation, the tool-call repair
(`websocket_tools::prepare_fallback_turn`). Those steps now build only the frame for an
attempt that is not native (another provider), and they cannot refuse a frame that a native attempt may carry. When
they cannot convert a `response.create` (for example a string or `null` `input`), their
error stops every attempt that is not native, before anything is sent, and the client
gets the same error frame as before on a connection that stays open. Every Codex turn is
native, a turn over HTTP included (#28). A missing previous response is connection state, not a
property of the frame, so it is still refused locally. The server keeps the frame's own
bytes, binary frames included, until the request boundary reads them. A frame that is
not UTF-8 is refused with the boundary's error, not forwarded with replacement
characters. The executor has no shaping,
payload rules, prompt-cache key in the body, reasoning replay, ID sanitizing, namespace
renames, Sign in with ChatGPT rules or `type` re-tag any more (#28). The prompt-cache
identity goes into the handshake headers only, and #26 owns those headers.

A native attempt is possible when the frame is a `response.create` and the selectable
credentials include a built-in Codex credential, with or without `websockets` (#28).
Under Home, every `response.create` counts. Selection then reads the client's own frame,
as on HTTP.

When the proxy's `codex.response-steering` setting is on, the connection keeps the
upstream socket after its first response. The proxy then reads each later client frame
through the [request boundary](#request-boundary). A frame that the boundary refuses gets
a local `error` event, and the connection stays open.

- A later `response.create` goes upstream with only `model` routed, as above.
- A create for another model cannot use this socket, so the connection closes with
  1012, the replay close.
- `response.steer` goes upstream as the client wrote it, without payload rules. The
  pinned client never sends this frame. OpenAI documents it for the GPT-6 family on the
  API, and nothing documents it for the ChatGPT backend. The upstream decides whether to
  accept it. The proxy adds nothing to it and makes no claim that it works.

The pinned client steers with a different sequence. It sends `response.interrupt` for
the running response, reads the acknowledgement and the interrupted
`response.incomplete`, and then sends a new `response.create`
(`responses_websocket.rs:310-325` and 824-839). The proxy forwards each of these frames
unchanged, with or without `codex.response-steering`.

A prewarm goes upstream, and its continuation stays on the same socket. The proxy never
sends a prewarm or any other request of its own, so it sends no inference keepalive.

### Socket and account ownership

One client connection uses one upstream socket on one credential. A continuation runs
only on the session's current socket. Under Home, the connection pins the pick that Home
granted. The pin holds while Home still keeps that pick, the continuation names the
model the pick was granted for, and Home's availability snapshot still allows the
credential. The local model registry does not need to list Home's provider. A healthy
continuation therefore reuses the pick and its socket, with no fresh pick and no
reconnect. A pick that is lost or released, a credential that Home's snapshot marks
unavailable, or a continuation for another model drops the pin, and the continuation
closes with 1012. When it cannot, the connection closes with 1012,
and the continuation never moves to another socket or account. When the upstream socket
is lost, the client connection closes, and the client recovers on its own. A request
the upstream may already have read is never sent again on another socket or account:
once its `response.create` was written, a loss before anything reached the client (a
close with any code, a dropped connection, an idle timeout), and a write that failed
after it may have sent part of the frame (a timeout, an I/O error or a reset), fail the
turn with a request-scoped error that neither fails over nor cools the credential, and
the client connection closes as for any lost socket. That holds under
`stream-bootstrap-buffering` too, after `response.created` or `response.metadata` was
held. Only a request that provably never left (the socket's loss was recorded before the
write, or the WebSocket library refused the frame before queueing it) is retried, once,
on a fresh socket, and an explicit upstream rejection (a wrapped status error, a
failure event) keeps its failover. A write is provably unsent when it failed or timed
out before the frame was handed to the WebSocket library; one that failed or timed out
after the hand-over may have sent part of it. The same rule holds for a turn served over
HTTP ([WebSocket HTTP fallback](#websocket-http-fallback)) and for the
[native HTTP route](#native-http-route): only a request whose connection could not be
made, or that never left because its deadline had passed, may fail over. After a
success status, or after a request was sent and the answer was lost, the failure is
request-scoped: no other account gets it, and a WebSocket client's connection closes. The first-party client reads such a loss as a
stream error (`responses_websocket.rs:1002-1005`) and retries the sampling request
itself (`core/src/responses_retry_tests.rs:17-50`); the proxy makes no copy (N1 #111). A loss
reported while the turn's request has not been served yet is the loss of a socket its own
attempt already failed on: it does not close the connection, and the turn fails over to
another credential or delivers that failure itself. Each socket's loss is its own. The loss of the
socket that then serves closes the connection like any other, idle or during a response,
and a failure on that socket renders its own error, never the loss let pass during
failover. A replaced socket's late loss reports nothing. A loss renders only in place of a
failure of the attempt that acquired that socket. An attempt that fails before it serves
on a socket (over HTTP, on another provider, or refused while it prepares its request)
fails with its own error. Once a new attempt starts, a socket already lost reports nothing
more, while a live socket keeps its own loss. The loss of a retained socket that the
current attempt did not acquire (the turn runs over HTTP or on another provider) does not
end that turn. A continuation always needs the socket that holds its previous response,
whatever transport the connection's last turn used: when that socket is gone, the
continuation closes with 1012 and nothing reaches the upstream. On a new
connection, a `previous_response_id` from the old one is refused locally with
`previous_response_not_found`, and nothing reaches the upstream. The duplex queue is
bounded:

- at most 16 outstanding creates;
- a write queue of 16 frames;
- 16 local items waiting for the client;
- at most 64 steers in flight on a `codex.response-steering` connection.

The proxy reads client frames only while the write queue has room, so a stalled
upstream backpressures the client. A full queue ends the connection with a local error.

A steer is in flight from admission to the upstream writer until upstream releases it: a
`response.steer.failed` for it, or, once accepted, the `response.created` of its
parent's successor or a `response.steer.failed` that names its ID. The settings that
steering pins for an automatic successor stay only while a steer in flight names their
parent. The ceiling of 64 is the proxy's own resource policy. No first-party or
documented source sets a limit, and the pinned client sends no `response.steer`. The
ceiling is separate from write backpressure. Socket buffers and frame sizes determine
which limit a stalled upstream reaches first. It also stops an upstream that reads
every steer and releases none.

- A client steer that would be the 65th ends the connection with a local,
  request-scoped error before it is written. The credential is not cooled, and nothing
  is replayed. Records still open fail with that error, as for the create bound.
- An acceptance that names no steer in flight, under a new ID, still counts, as in Go.
  A repeated ID replaces its entry, so it does not count again. An acceptance that
  would be the 65th reaches the client as sent, and the connection then ends with a
  local, request-scoped error. That makes no claim about what the upstream meant.

### Responses and failures

The client receives each upstream text frame as it arrived. The proxy repairs no output,
renames no `response.done`, adds no usage details, restores no namespace and reconciles
no tool calls. Usage, capture, quota observation and failure classification read a copy.
Leading events are held under `stream-bootstrap-buffering`, but they are never changed.

Every upstream failure frame keeps two readings: the scheduler's classification, which
drives failover and credential health, and the frame itself, which is what the client
receives (`ExecError::delivered_event`). Classification reads the frame as the pinned
reader decodes it (`codex_event::classification_view`), on every native path: serde
reads a derived struct from a JSON array by position, so a `ResponsesStreamEvent` such
as `["response.failed",null,null,{"id":"r1","error":{…}},null,…]` or a wrapped status
error such as `["error",429,{"code":…}]` is read as the object of the members it
decodes to, each value as sent, a `null` member absent and nothing outside the struct
added (a positional event has no `status`). Members are then read with the last of a
repeated key and private values resolved. A `Value` member that is an array stays one,
with one exception: a `response.failed`'s `response.error`, which `parse_failed_response`
reads into its `Error` struct (`sse/responses_error.rs:14-24`), so also by position. Five
or six members, each `null` or of its member's type, read as the object of those members
(`type`, `code`, `message`, `plan_type`, `resets_at`, `misalignment`), and the failure
classifies as that object does; any other array is one that struct refuses, which the
pinned reader reports as its generic stream error, and it stays an array. An `error`
event's `error` is read only by `Value::get` there (`parse_terminal_provider_error`), so
an array in it stays one.
Account safety reads a failure slot by position even when its typed decode refuses it
(`codex_event::safety_views`), because processing eligibility and safety are separate
facts: a refused struct still carries what the upstream wrote in it. A `response.failed`'s
refused `response.error` array, and its own `error` array, which the proxy's failure
reading falls back to, are named as `Error` names its members; an `error` event's `error`
array as `WrappedWebsocketError` names them and as `Error` does; and a frame written as an
array that neither `ResponsesStreamEvent` nor `WrappedWebsocketErrorEvent` accepts as each
of those structs names its members, extra elements left out. That reading never classifies,
settles or cools; it only decides whether the client may receive the frame.
A status-less context-window `error` written that way becomes the #5 `response.failed`
built from the bytes of its members.

- A failure that is not an account failure reaches the client as the upstream sent it.
  This covers `response.failed`, a status-less `error` and the wrapped status `error`
  frame: unknown members, `null` and number spellings included. The proxy builds no
  error of its own.
- A failure before anything was delivered fails over when its classification allows it
  (a retryable status, an overload) and the upstream explicitly rejected the request; a
  lost socket after the write is no rejection and never fails over ([Socket and account
  ownership](#socket-and-account-ownership)). Once the attempts run out, the client receives the
  last attempt's frame. That includes a Home round that ends with a retry hint, which
  wraps the upstream error in its retry metadata.
- A failure after the response started reaches the client after the events before it.
  Without `codex.response-steering` the connection then closes. With it, the first
  response's failure is handled like a failure before anything was delivered, and a later
  failure is an event that the client may correct on the same socket. That recovery
  belongs to the Go-defined steering transport; the pinned client does not use it.
  The proxy ends the socket after delivering a failure it cannot safely associate with
  a running response or pending create. Started-response settings retain 16 starts.
  After any eviction, an unmatched failure ID is ambiguous because it might name a
  forgotten settled response. Open and retained IDs still identify their own responses.
  Before eviction, assigning an unmatched ID to the oldest pending create is inherited
  proxy policy from Go, with unknown provider applicability. The pinned client supplies
  no FIFO ownership rule for steering failures.
- A decoded event names its response by the `response.id` the pinned `Value` reads: the
  last of a repeated `id`, with private values resolved (`Event::response_id`). A
  `response.completed` whose `response` reads as `ResponseCompleted` names the
  response that reading carries, the same decoding that decides it ends the response:
  `ResponseCompleted` written as a JSON array (serde's positional struct form) names
  its first element, which `Value::get` would not find; `response.created` and every
  other event keep the `Value::get` reading. A
  steering connection binds a `response.created` to that ID, feeds usage to and settles
  the response it names, and an ordinary turn and the interrupt bookkeeping end that
  response. Delivery keeps the event as sent.
- An account failure (classified 401, 402, 403 or 429) never reaches the client as sent,
  on any path: an ordinary turn, the first or a later response of a steering connection,
  or a create still waiting in the duplex queue. Its frame can name the pooled account or
  carry its tokens. The client gets the allowlisted subscription-limit event when it is an
  official Codex client (#6), or else a silent close. The scheduler still receives the
  classification, so the credential cools as before. The same holds for a failure whose
  own error is an account failure under the status-frame or terminal failure reading, read
  as the pinned reader decodes the frame (`codex_ws::account_sensitive`: the last of a
  repeated key, private values, positional structs), or read by position where a pinned
  struct refuses the slot (above): the pinned wrapped mapping keeps an
  explicit `status: 400` beside a rate-limit error, so the scheduler records that 400 and
  cools nothing, while the frame is withheld; a `response.failed` whose refused
  `response.error` array reads as a rate limit by position keeps the generic 502 and its
  cooldown, while the frame is withheld. A failure whose error is one of the pinned
  client's account kinds is withheld too, whatever status Go's table gives it
  (`codex_ws::pinned_account_kind`): `RateLimitExceeded` (`rate_limit_exceeded`,
  `slow_down`), `QuotaExceeded` (`insufficient_quota`, `credit_balance_exhausted`,
  `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, and
  `organization_usage_limit_exceeded` on a 429) and `UsageNotIncluded`
  (`usage_not_included`), read from a `response.failed`'s `response.error` or own `error`
  and an `error` frame's `error` or `body.error` (`sse/responses_error.rs:48-103`,
  `api_bridge.rs:136-140,212-255`); the types `usage_limit_reached`,
  `usage_not_included` and `insufficient_quota` count the same. Their message, plan and
  reset describe the pooled account. Only delivery changes: Go's table still classifies
  `slow_down` and `insufficient_quota` as 502 and `usage_not_included` as it did, so
  cooldowns and failover are unchanged. A decoded failure whose first repeated
  `type` is a rate limit but whose last is not is no account failure, as the pinned
  `Value` reads it, and reaches the client as sent. Withheld
  means the client also gets no rendering of the frame's error (the error the server would
  otherwise build from the classified body, or a close reason taken from it): the decision
  travels on the error (`ExecError::delivery`), so it holds wherever the failure ends the
  connection, after bootstrap failover and as the session's loss too. On a steering
  connection such a later failure ends the connection like an account failure, failing
  every open record and queued create with its classified status.
- One exception stays: a Codex client gets the status-less context-window `error` as
  `response.failed` (#5).
- Every frame passes the upstream event boundary of the
  [native HTTP route](#native-http-route), on an upstream socket, a steering connection
  and a turn served over HTTP. The WebSocket reader has one more reading. A frame that
  is not a `ResponsesStreamEvent` can still be a wrapped status `error`
  (`responses_websocket.rs:684-709`, 864-884), decided as the next item describes. The SSE reader has no such reading, so over HTTP
  it is a frame that does not decode. A frame that does not decode passes as sent and
  ends, fails and settles nothing, with one exception. When its failure reading would
  be an account failure, it is withheld, because it can name the pooled account. That
  reading takes the first and the last of a repeated key (a JSON reader keeps one or
  the other) and, when a member the failure readings read repeats (`type`, `status`,
  `status_code`, `error`, `code`, `message`, `error_type`, `response.error`, and the
  `type`, `code`, `status`, `status_code` and `message` of either error object), every
  other occurrence too, since a reader that acts on members as they stream past can
  take any of them (`crates/cpa-exec/src/codex_ambiguous.rs`), and the frame's `param`,
  which a status-less reading copies. A member repeats when its path does: the same key
  twice in one object, or inside a repeated ancestor such as the frame's `response`.
  `error.type` and `response.error.type`, once each, repeat nothing. Each occurrence is checked on its own, in one pass,
  except the capacity check, which reads the error body a reading composes from several
  members (the error object as sent, the frame's `message`, `code`, `error_type` and
  `param`, and a message taken from the other error object): one summary of every piece
  any reading could compose decides it, so `model` in one member and `at capacity` in
  another count together. An ambiguous frame can therefore be withheld that no single
  reading classifies as an account failure; the pinned client skips it either way. A
  private number or raw value is read as sent and as the pinned `Value` reads it. A
  frame written as an array that neither pinned struct accepts is also read by position
  (above), so a wrapped error array whose `error.code` is a private raw value is withheld
  when it reads as an account failure. It
  is not classified either, so the credential does not cool and the turn goes on. A
  decoded frame keeps the pinned last-key classification.
- On an upstream socket a wrapped frame (a frame that does not decode, or a decoded
  `error`, that decodes as `WrappedWebsocketErrorEvent`) is decided by the pinned
  mapping (`responses_websocket.rs:712-764`). `previous_response_not_found` and
  `websocket_connection_limit_reached` fail the turn whatever the status, and reach
  the client as sent. A status `http::StatusCode` accepts (100 to 999) that is not a
  success fails it by that status. A success status, or one outside 100 to 999, maps
  to no error: the frame is a notice that passes as sent (or is withheld when it would
  read as an account failure), ends nothing and cools nothing. A decoded notice still
  fails the turn when the pinned `error` branch raises its logical code (including
  an error object or code represented by a private raw value)
  (`parse_terminal_provider_error`, `error.rs:79-127`). A decoded `error` that carries
  a status but is not a wrapped frame is a notice too, whatever Go's integer reading
  makes of the status: the pinned reader has no wrapped event and goes on to the `error`
  branch, which reads no status (`sse/responses.rs:375-385`). That covers a status the
  wrapped struct cannot read as a `u16` (negative, too large, a fraction or exponent
  such as `429.0` or `4.29e2`, a string such as `"429"`, `" 429"` or `"+429"`, a private
  number or raw value, a container) and a frame the struct refuses for another member
  (`status` beside `status_code`, a repeated `status`, a private raw value as
  `error.code`, which `WrappedWebsocketError` cannot read as a `String`); zero, which
  `StatusCode::from_u16` refuses, is a wrapped notice already. Such a frame is checked
  for a terminal provider code, which still fails the turn (by the status-frame reading's
  status when that is an error status, else by the terminal failure reading), and
  otherwise passes or is withheld as account-shaped; the turn goes on and nothing cools.
  `codex_pinned_notice_readings.json` records the pinned decision for each spelling. Only
  a decoded `error` with no status at all (every `status` and `status_code` missing or
  `null`) keeps the status-less failure reading above. Over HTTP the SSE reader has no wrapped reading, and the proxy's HTTP reading
  stays as described for the native HTTP route.
- Every `response.incomplete` reaches the client as received, on an ordinary turn, a
  steering connection and a turn served over HTTP, at any stage: as the turn's first
  event, after events held for bootstrap, or after output. The socket stays for the next
  turn, and the credential does not cool. A WebSocket client's turn ends on a
  processing error as on a terminal event (a content filter, or a `response` that does
  not read as `ResponseCompleted`), because the pinned WebSocket reader returns that
  error and retires its socket; on a turn served over HTTP too, although the SSE
  upstream would have more to read. Its record carries the event's reported usage, not
  failed. A steering connection relays every frame, so a later completion also reaches
  the client, which decides. Passive accounting records the response once,
  as it records any terminal event the provider sends. An upstream socket that closes or
  fails before the terminal event still ends the turn with that failure, and the proxy
  invents no terminal event for it.
- A steering connection's duplex reads the client's later frames once the first
  response's `response.created` has reached the client. When upstream ends the first
  response without one, the duplex starts reading once that terminal event has reached
  the client. Only the bootstrap create was outstanding, so that terminal event settles
  it. Its usage record is published once, with what the terminal reported, and later
  creates get records of their own. The next create runs on the same socket with the
  bootstrap's settings. The proxy invents no `response.created`, and the terminal's
  response ID binds no retained settings. Go reads later frames only after a
  `response.created` (`codex_websockets_duplex.go:391`, 601-605), so a create sent on
  such a connection waits there with no answer. Whether a provider sends that shape is
  unknown. The pinned client does not use the steering transport.
- The interrupt regressions stay. An interrupt acknowledgement that arrives after the
  terminal event is still delivered. A late interrupt does not poison the next turn. An
  interrupted `response.incomplete` passes unchanged.

### Handshake metadata

The proxy's downstream 101 is sent before the first request chooses a credential and a
model, so it cannot carry the upstream handshake. The pinned client also reads two of the
handshake's headers from a `response.metadata` event (`sse/responses.rs:193-222`), and
the proxy delivers them that way. [Permitted transformations](#permitted-transformations)
lists this edit. The headers have different lifetimes in the pinned client, so the proxy
delivers them differently.

| Header | Pinned client | Proxy |
| --- | --- | --- |
| `x-codex-turn-state` | Set from the upgrade (`responses_websocket.rs:623-630`) or from a `response.metadata` event's top-level `headers` (`sse/responses.rs:214-222`, `responses_websocket.rs:934-938`). The turn's `OnceLock` keeps the first value; a new logical turn starts with a new lock (`core/src/client.rs:323-343`). | Delivered once, to the request that opened the socket. It is never repeated on a reused socket: in a later turn's new lock it would be a stale first value. |
| `openai-model` | Read from the upgrade (lines 618-622) and re-emitted as `ServerModel` at the start of every request on that socket (lines 302-303). Any event can also carry it, in `response.headers` first and top-level `headers` second (`sse/responses.rs:193-212`); each response stream suppresses consecutive equal values, so A -> B -> A reports A again (`responses_websocket.rs:948-963`). | Delivered to the request that opened the socket, and alone to each eligible later request on it under the omission rules below. |
| `x-reasoning-included` | Read from the upgrade (`responses_websocket.rs:617`) or HTTP response headers by presence only, and re-emitted on every request (lines 304-308). No event sets it. | Not delivered. |

The rules for the proxy's event:

- The opening event carries `x-codex-turn-state` and `openai-model`, each only when
  present and not empty after trimming. It comes before the first delivered event of the
  request that opened the socket, including a send retried on a fresh socket.
- Each eligible later request on the same socket gets `{"type":"response.metadata","headers":{"openai-model":...}}`
  before its first delivered event. "Later" counts requests, not user turns: the first
  real request after a prewarm, each continuation and each new logical turn. The pinned
  client's startup prewarm drains its own notifications and keeps only completion
  (`core/src/client.rs:2550-2557`), then hands the same session to the real request
  (`core/src/tasks/regular.rs:100-131`). Without this event, that request would get no
  model notification at all.
- A socket opened on a later request delivers its own opening event, with its own turn
  state. The value always comes from the socket that serves the request. A failed write,
  a refused or failed upgrade, an attempt that failed over, a Home pick that was lost or
  a replaced socket never supplies it. A socket whose upgrade had no model repeats
  nothing, even when an earlier socket had one.
- Omission is decided for each request. `openai-model` is left out when the model the
  proxy sent upstream differs from the model that request named, comparing ASCII case
  only as the pinned client does (`core/src/session/mod.rs:4650-4688`), so that an alias
  or a payload rule never looks like a cyber-safety reroute. A native thinking suffix is
  refused before this point. When the current upstream model matches the socket's
  opening request model and the proxy did not rewrite it, a differing upgrade model
  stays visible.
- Additional proxy policy: omit the synthesized model on a later request whose upstream
  model differs from the socket's opening request model, comparing ASCII case only.
  The pinned client instead repeats its stored upgrade model unconditionally
  (`responses_websocket.rs:277,302-303`). It can send a changed model on the same socket
  (`core/tests/suite/client_websockets.rs:2478-2555`). This fork chooses omission to
  avoid treating an earlier model's announcement as a reroute for the new model.
  Whether the backend's upgrade model still applies after a switch is unknown.
  Omission can therefore hide a still-applicable reroute notice. This policy does not
  establish which model served the request. Upstream event metadata still passes
  unchanged.
- On a response-steering connection, an explicit later `response.create` gets the event
  right before the `response.created` that starts it. A create rejected before it
  starts gets none, and neither does an automatic successor, which upstream starts on
  its own. The pinned client does not use `response.steer`, so no steering rule follows
  from these sources.
- Metadata that the upstream puts in an event reaches the client inside that event,
  unchanged and in order, after the proxy's event. The proxy never edits, replays or adds
  an upstream frame, and its event is not counted as provider output or usage.

The repeated model is upgrade metadata, as in the directly connected client. It does not
show which model served each generation. `x-reasoning-included` has no event consumer in
the pinned client, so copying it into JSON could not deliver it, and the proxy never
infers it from body content. Reasoning-included metadata stays undelivered.

### WebSocket HTTP fallback

A Codex credential without `websockets` has no upstream socket, so a turn on it goes
upstream as one HTTP Responses request (#28). The first-party `response.create` frame is
the HTTP request plus its `type` tag (`codex-api/src/common.rs:315-339`, 400-406), so
the conversion removes `type`, routes `model`, and sends `stream: true` when the frame
omits `stream` or sets it to `false`: a WebSocket turn always delivers events, so the HTTP
request asks for the event stream. Nothing else changes. An upstream that answers with a
success that is not an event stream fails the turn with a credential-scoped 502 before
anything reaches the client; the proxy delivers no aggregate and invents no event. When a requested HTTP event stream has no Content-Type header, the proxy inspects
at most 64 KiB of its initial framing (an optional UTF-8 BOM, empty lines, then a
standard SSE field or comment). It replays every inspected byte unchanged. A
missing MIME header alone does not establish a non-stream response. Explicit
media types remain authoritative. This also applies to native HTTP streaming
and the ChatGPT buffered-to-stream adaptation. This is a transport compatibility
rule based on the fork deployment captures, not a new endpoint guarantee.
The upstream's
SSE events reach the client unchanged, one event's `data` payload per text frame, with
the connection as prompt-cache identity in the headers. Failures follow the native
WebSocket rule: a Codex client's context-window event goes ahead of the error (#5), any
other failure travels on the error as sent, and an account failure never reaches the
client as sent ([Responses and failures](#responses-and-failures)).

- A first turn goes upstream as described.
- A continuation (`previous_response_id`) needs state that only an upstream socket
  keeps. It closes the connection with 1012, the replay close, and nothing reaches the
  upstream. The pinned client then reconnects and sends the full conversation, which
  is a first turn on the new connection. Go answered it from a transcript the proxy kept
  and merged; that hidden history is gone for Codex.
- A prewarm (`generate: false`) is refused with a 400 `invalid_request_error` that names
  the cause and the fix: there is no upstream socket to prewarm, and the proxy does not
  invent a response. Nothing reaches the upstream, and the connection stays open. This
  applies when the pinned credential is a Codex credential, or when nothing is pinned
  and the model's pool holds one. Under Home, before the connection's first pick, no
  credential or transport is known, so a prewarm is refused the same way, without a Home
  pick, with a message that says so. After a pick on an upstream socket, a prewarm goes
  to the provider on that socket. Go answers such a prewarm locally with a made-up
  `resp_prewarm_` response; other providers keep that behaviour.
- An interrupt (`response.interrupt`) has no upstream socket to go to. For the running
  response, the proxy cancels the HTTP request, sends
  `{"type":"response.interrupt.accepted","response_id":...}` with the interrupt's ID, and
  then sends a `response.incomplete` with that ID, `status: "incomplete"`, the reason
  `interrupted` and the output items the provider already delivered. The proxy adds no
  usage and no text, and never sends a successful completion. An interrupt for the
  response the connection just finished gets the acknowledgement alone. The pinned
  client reads only the ID, the reason and the usage of an interrupted response
  (`sse/responses.rs:451-518`), and ends the turn with `end_turn: false`. These events
  answer the client's cancel handshake. They are not provider output, and nothing
  further reaches the upstream (#1,
  [DIFFERENCES-FROM-GO.md](../DIFFERENCES-FROM-GO.md)).

The server's transcript merge, tool-call repair and Codex-client preparation still build
the frame that other providers receive; no Codex attempt sees it.

An upstream handshake that answers 426 fails the turn with that status. No proxy-side
HTTP conversion follows. The pinned client's own HTTP fallback runs only for its own
upgrade, and the proxy's downstream upgrade has already succeeded.

## Credential isolation

An upstream can write the authentication value it received into its answer: an error
message that quotes the bearer token, a close reason, a header. The native routes deliver
the upstream's own bytes, so they check every delivery against the values the request
that produced it actually carried (`crates/cpa-exec/src/codex_secret.rs`, #25 acceptance
criterion 7). This is a backstop for the selected credential. It is not the #6 account
reading above, which decides by what a failure means.

- **Which values.** The values are the credential of each `Authorization` header (the
  token after `Bearer`), each cookie value, each API-key header, and a password in the
  URL, taken from the request as sent upstream: the HTTP request, or the handshake of the
  socket that reads the frame. A reused socket keeps its own handshake's values, even
  after the credential was refreshed. A fresh dial, a refreshed HTTP request and a
  failover attempt each get their own. Routing, account, session and cache identities
  (`chatgpt-account-id`, `session_id`) are no authentication values. Neither is the same
  text from another account, a saved login or a configured credential that this
  request did not carry. Empty values match nothing.
- **Which spellings.** The check reads the original bytes, whatever a parser makes of
  them. It covers a frame the pinned client cannot decode, a repeated member that a
  last-key reader drops, an array, an opaque or refused failure slot, a private raw value
  and invalid JSON. A value counts as written and under up to 16 rounds of JSON
  unescaping over every byte (`\"`, `\\`, `\/`, the control escapes and `\uXXXX`, surrogate
  pairs included), so an escaped spelling and a raw value's string inside a string count
  too. Bytes still unescaping after the last round count as carrying a value. An HTTP
  stream is checked event by event, after the shared SSE framer has joined its chunks.
- **What it changes.** Delivery only. Eligibility, classification, settlement, cooldown,
  usage and the pinned outcome are decided before the check and stay as they are.
  - A frame that carries a value is not delivered, and the response goes on as the
    processing decided. For a frame the pinned reader skips, or a notice, the real
    completion follows and nothing cools. For an ordinary event, only that event is
    missing. For an event a WebSocket turn ends on, the turn ends without it: an upstream
    socket's turn closes silently (the server's "stream closed before
    `response.completed`" close), with its record and usage as processed. An HTTP stream
    ends without the event, so the client reads a stream that closed before completion.
    On a steering connection, such an event, or a later failure that carries a value,
    ends the connection with a silent close, because the client would otherwise wait for a
    response that already ended. The response's own record is settled as processed, and
    every other open record and queued create fails with the connection.
  - A frame that is not delivered was still served: the executor processed it, so the
    stream commits on it as on a delivered frame (`ExecResponse::omitted`,
    `dispatch::finish`). A response whose every frame is withheld, its terminal event
    included, keeps the outcome processing gave it: one execution, a successful record
    with the usage the upstream reported (none when it reported none), no cooldown. It
    is not Go's empty stream (`empty_stream`), which cools the credential and runs the
    request again on another one. A failure or a truncation after a withheld frame stays
    a failure after delivery, as after a delivered one, an account failure included: it
    fails the request and is never retried on another account. A steering connection
    processes its frames before the stream does, and hands the stream every frame it
    processed, so the stream's guard alone leaves one out and records it.
  - A failure that carries a value, in its body, the frame it would deliver as sent, or
    a header it hands the client, becomes `Delivery::Confidential`. Its classified status
    and scope stay the scheduler's (no conversion to 429). The client gets no frame, no
    rendering of the body, no subscription-limit event, no close reason and no
    passthrough headers: a WebSocket client gets a silent close, and an HTTP client gets
    an error rendered from the classified status alone. This also holds when the failure
    ends the connection after bootstrap failover, as the session's loss, or as an
    interrupt's rejection. A cooldown that such a failure starts keeps only its status as
    the "last error" that a later request's cooldown answer shows.
  - A buffered or compaction answer that carries a value fails with a request-scoped
    502 (`codex upstream response withheld: it carried the upstream credential`). It does
    not fail over, because the upstream served it, and it does not cool the credential.
    Its record is a failure without tokens. A buffered client has no stream to end.
  - An upstream response header that carries a value is dropped. An interrupt
    acknowledgement that carries one is not delivered.
- **What stays.** A frame without such a value keeps every byte: spacing, number
  spellings, duplicate members, unknown fields and opaque arrays.
- **Logs and records.** The request log (`crates/cpa-server/src/request_logging.rs`) and
  the usage record keep what the upstream answered scrubbed of the same values
  (`cpa_core::sent::SentCredentials::scrub`): each value as written becomes `[REDACTED]`,
  and an entry that still carries one in an escaped spelling keeps only its length. This
  covers every log section and its spool file, the `api.websocket.*` events, the
  WebSocket timeline's disconnect entry, and every text of the upstream's answer a record
  keeps: `fail.body`, `response_headers`, `response_model` and `response_service_tier`
  (`usage_record::Record::upstream_text`). The values are bound as delivery binds them:
  the request's until a socket serves the turn, then that socket's handshake values; a
  fresh dial, a refreshed request and a failover attempt bring their own. The binding
  belongs to the connection, so every record on it, a steering connection's later
  responses included, is scrubbed of its socket's values whichever publishes first. A
  record's status, tokens, account and every other field stay as processed. The request
  body is the client's own bytes and is logged as sent.
- **What it does not cover.** The translated route (#27) and other providers have no
  such guard.

## Translated route

[#27](https://github.com/zakstak/cliproxy-rs/issues/27) puts this route in place. A
request takes it when all of these hold:

- its client format is Claude Messages or Chat Completions; each has a registered
  built-in pair into Codex. The Gemini and Gemini Interactions sources went with those
  client protocols (issue #49): their routes answer 410, and the rows and refusals
  below that name them are historical;
- the selected credential is a built-in Codex credential, on any profile;
- it is a generation (not compact or a token count).

The `siwc` profile takes it too (#28): the conversion is the same on every profile, and
no profile-specific rule is added.

### Requests

The request is converted by its pair's built-in converter in strict mode
(`cpa_translate::codex_request`). The request's own fields are then checked by
`cpa_translate::codex_strict`. Nothing else edits it:

- No payload rule runs.
- Nothing is synthesized: no prompt-cache key, no default `instructions` (the pinned
  client sends none: `codex-api/src/common.rs:286-314`), and no reasoning effort the
  client did not choose.
- Nothing is rewritten: no input-ID rewrite, no tool injection (image generation, web
  search), no schema or `parallel_tool_calls` normalization, no call-ID shortening, no
  namespace optimization.
- No hidden history: the reasoning-replay cache is deleted.

Every source field has a rule. It maps to its Responses field, is accepted only at its
API default, is converted with a check on its value, or is refused.

Two transport edits follow the conversion: the routed `model`, and `stream: true`. The
response is translated from the upstream's events either way, and a buffered client
receives their aggregate. The prompt-cache identity reaches the handshake headers only;
#26 owns them.

The server's own request and response interceptors still run on the client's own
format, as they do for every provider: they are outside the Codex wire. A request whose
hooks read unframed stream payloads keeps the translated route, and the executor hands
those hooks the client's payloads.

The registered pairs keep Go's conversion, because the meta and xAI executors share them.
The strict mode is the Codex route's alone.

#### Refusals

Any request field, control, content part or tool that Codex cannot express is refused
with a 400 before any upstream request, and the message names it.

Request fields and controls:

- any top-level field without a rule;
- Claude `top_k`, non-empty `stop_sequences`, `service_tier: standard_only` or another
  tier other than `auto`, `fast` and `priority`, an unknown `speed`, an unknown
  `tool_choice` type (or `tool` without a name), an unknown `thinking` type, or an
  `output_config` member other than `effort` and `format`;
- Chat `stop`, `n` above 1, a non-zero penalty, `seed`, `logit_bias`, `logprobs`,
  `store: true` (the encrypted-reasoning round trip needs `store: false`), audio or
  other non-text modalities, a message `name` or `refusal`, or a `response_format`
  type other than `text`, `json_schema` (with a schema) and `json_object`;
- Gemini `topK`, `stopSequences`, `candidateCount` above 1, a `responseMimeType` other
  than `text/plain`, `safetySettings`, `cachedContent`, a tier other than `priority`,
  `fast` and `standard`, a function-calling mode other than `NONE`, `AUTO` and `ANY`
  (such as `VALIDATED`), allowed names with a mode other than `ANY`, or an allowed name
  that no declaration has;
- Interactions penalties, `stop_sequences`, `response_format` or `store: true`.

Content, including content nested in tool results and system prompts:

- Claude `redacted_thinking`, server tool blocks and other unknown blocks;
- a thinking block with reasoning text or a signature that is not Codex encrypted
  content, and a thinking block outside an assistant turn;
- a document that is not an inline PDF, at the top level or in a `tool_result`;
- any other block in a `tool_result`;
- a `tool_result` with `is_error: true`: Responses `function_call_output` has no failure
  status, so the result is refused rather than sent as an ordinary result;
- a non-text system block;
- a tool without an object `input_schema`, or a deferred tool (`defer_loading: true`);
- a Chat `refusal` part, an audio part without data, a tool result without its call, a
  duplicated call ID, or a call of an unknown type;
- Gemini `executableCode` and other parts it cannot convert, a thought with text, a
  system part that is not text, and built-in Gemini tools such as search;
- an Interactions thought step, a step with no content, or a part with no Responses
  form.

A sample message: `unsupported conversion: \`top_k\` has no Codex Responses
equivalent; remove it or send the request to a provider that accepts it`.

### Responses

The same pair's built-in response translator converts the upstream's events, without
namespace restoration. A buffered client receives
the translation of the aggregated terminal event. Usage is the provider's. A Claude
client's `message_start` carries what the translator knows (zero input tokens before
the response ends), not a local estimate, and its final `message_delta` carries the
provider's counts. Upstream errors keep their classification and reach the client in
its own error format. Until #27 replaces it, the translator keeps Go's empty-incomplete
rule: a `response.incomplete` with no output item, no output delta and
`output_tokens` 0, whose reason is missing or is not `interrupted`, `content_filter` or
`max_output_tokens`, becomes a request-scoped 502. The native routes no longer apply it
([Permitted transformations](#permitted-transformations)).

### Token counts and images

A token count reads the body the request would send: the client's own bytes for a
Responses client, after the [request boundary](#request-boundary), or the strict
conversion. No Codex-client rewrite, default or payload
rule changes it. The response carries `x-cliproxy-token-count: local-estimate`, because
the number is this proxy's tokenizer estimate, not provider usage.

The Images API adapter has two paths. Neither runs payload rules or input-ID rewrites,
and neither synthesizes a prompt-cache key. Both read the client's JSON through the
[request boundary](#request-boundary) first.

- A direct request (an image model on the direct list, or a configured API-key image
  model) reaches the provider's Images endpoint as the client sent it, with only its
  model and `stream` routed.
- The tool adapter builds a Responses request containing only what the conversion
  needs: the model, the forced `image_generation` tool with the client's image
  settings, the prompt and images, `stream: true` and `store: false`. It sends no
  default `instructions`, reasoning, `parallel_tool_calls` or `include`.
- In an edit, each image and the mask keep their reference form: `image_url` (a data URL
  included) or `file_id`, as the Responses `input_image` and `input_image_mask` take
  them. An image or mask without exactly one of the two is refused.
- Images fields the tool cannot express (`style`, `user`, `n` above 1, and others) are
  refused, in JSON and multipart requests alike. A multipart edit is also refused for a
  file field other than `image`, `image[]` or one `mask`, or for `image` and `image[]`
  together.
- #33 owns the image model IDs.

### Remaining limits

- A Gemini `thoughtSignature` is not sent: it is Gemini's state for its own model, and
  no other model reads it.

## Responses, errors and interruption

Provider responses reach the client as the upstream sent them, on every transport.
Passive accounting reads a copy and changes nothing.

- Events. The proxy forwards every event, including those it does not model, such as
  `response.output_item.interrupted`, `codex.rate_limits`, `codex.response.metadata` and
  `responsesapi.websocket_timing`. It renames no event and drops no field.
  `codex-api/src/sse/responses.rs:375-562` lists the events the client decodes.
- Usage. `usage` is optional in `response.completed` (`sse/responses.rs:111-118`).
  Missing usage stays missing. Zero stays zero only when the upstream reported zero.
  `input_tokens_details.cache_write_tokens` and the documented
  `cache_write_tokens_details` pass through.
- Structured failures. The client classifies `response.failed` by `error.code`
  (`sse/responses_error.rs:26-106`): `context_length_exceeded`, `insufficient_quota`,
  `usage_not_included`, `cyber_policy`, `bio_policy`, `misalignment_policy_violation`,
  `invalid_prompt`, `server_is_overloaded`, `rate_limit_exceeded` and others. For
  `rate_limit_exceeded`, it parses the retry delay from the message text (lines 108-128),
  so the message must arrive unchanged.
- HTTP errors. A 429 with `error.type: "usage_limit_reached"`, `plan_type`, `resets_at`
  and `limit_window_minutes`, plus the `x-codex-*` rate-limit headers, becomes a usage
  limit in the client (`codex-api/src/api_bridge.rs:207-255`). Status, body and those
  headers reach the client.
- Terminal request rejections (FP2, #116, research main `5c3ff1dabf64`, not the pin).
  `error.rs:92-162` adds `inference_hook_denied` (no status or 403),
  `content_policy_violation` (no status or 400), `invalid_access_program`,
  `unsupported_access_program` and `access_program_not_enabled` (no status), and
  `api_bridge.rs:293-311` makes a 403 whose `/detail/code`, `/error/code` or
  `x-error-json` code is a workspace or access-program denial terminal. The client never
  retries them. The proxy stops the request on the selected account: no failover, no
  cooldown, no refresh. An in-stream event, and a WebSocket `error` frame the wrapped
  mapping leaves unmapped, are read with no status (an in-stream one takes the 403 or 400
  the code pairs with); a wrapped status frame or an upgrade refusal with its status.
  `context_length_exceeded` is a context-window failure only without a status or with
  400. Frames reach the client as sent, except that a 403 is withheld from a native
  WebSocket client (#6). `cpa_exec::codex_terminal` holds the rules and
  `ExecError::sourced` carries them to the scheduler;
  [FP2-TERMINAL-ERRORS.md](FP2-TERMINAL-ERRORS.md) lists the evidence and open gates.
- WebSocket errors. A wrapped `{"type":"error","status":...,"error":...,"headers":...}` frame
  is classified by `responses_websocket.rs:712-764`. `previous_response_not_found` and
  `websocket_connection_limit_reached` are retryable, and the client retries
  `previous_response_not_found` with full input on its own.
- Handshake metadata. The client reads `x-reasoning-included`, `openai-model` and
  `x-codex-turn-state` from the WebSocket upgrade response
  (`responses_websocket.rs:617-630`). It also reads `x-codex-turn-state` from a
  `response.metadata` event and `openai-model` from any event's headers
  (`sse/responses.rs:193-222`), and `x-models-etag` from a `codex.response.metadata`
  event (`responses_websocket.rs:919-933`). [Handshake metadata](#handshake-metadata) has the details.
- Interrupted and incomplete responses. `response.incomplete` with reason `interrupted`
  ends the turn with `end_turn: false`. `content_filter` is its own error. Any other
  reason, `unknown` when missing, is a terminal `ResponseIncomplete` that keeps the
  reason, response ID, partial output and usage, with no retry delay
  (`sse/responses.rs:451-506`, `protocol/src/error.rs:428-442`). It needs no preceding
  `response.created`. The proxy forwards every native `response.incomplete` as
  received, zero-output ends included, before or after anything was delivered. It never
  turns an incomplete or disconnected response into a successful completion, and never
  replaces an incomplete with a local failure.

## WebSocket state

- One client socket uses one upstream socket on one credential. A continuation, a
  prewarmed response ID or a pending interrupt never moves to another account or
  another socket. When the upstream socket is gone, the client sees the failure and
  recovers on its own.
- The proxy forwards a client's prewarm and never sends its own. It sends no inference
  keepalive. A prewarm that only the [HTTP fallback](#websocket-http-fallback) could
  serve is refused, never answered locally.
- The proxy forwards `response.interrupt` and its acknowledgements unchanged. On a turn
  served over HTTP, which has no upstream socket, the proxy answers the interrupt
  itself, as described in [WebSocket HTTP fallback](#websocket-http-fallback).
- A 426 handshake fails the turn with that status. The only proxy-side HTTP conversion
  is the [WebSocket HTTP fallback](#websocket-http-fallback) for credentials without
  `websockets`, which removes only the frame's `type`.
- [Native WebSocket route](#native-websocket-route) states the handling of
  `response.steer`, `response.append` and the steering queue. No PR may describe any of
  them as first-party behaviour.

## Implementation order

The order below keeps every route either fully on the old behaviour or fully on the
new one, and never half of a reversible rewrite.

1. [#22](https://github.com/zakstak/cliproxy-rs/issues/22) adds one shared, validated
   and lossless JSON boundary. It migrates parsing only where a caller survives the
   later PRs unchanged. It does not rewrite functions that #23 to #27 delete.
2. The native HTTP group takes [#23](https://github.com/zakstak/cliproxy-rs/issues/23),
   the HTTP parts of [#25](https://github.com/zakstak/cliproxy-rs/issues/25), and the
   route-local parts of #22 and [#28](https://github.com/zakstak/cliproxy-rs/issues/28).
   It moves complete paths, from ingress to the upstream send and back to the client.
3. The native WebSocket group takes #24, the WebSocket parts of #25, the parts of #3
   the proxy can resolve, and the route-local parts of #22 and #28.
4. Required translation, #27, and identity, #26, stay separate PRs.
5. Each migrated path blocks payload rules and other mutation hooks in the same PR
   (plugin normalizers went with native plugins, #47). A response restoration leaves in the same PR as its request
   rewrite.
6. #28 and [#29](https://github.com/zakstak/cliproxy-rs/issues/29) consolidate
   qualification across routes. They do not hold back safety that an earlier PR could
   ship.

Each implementation PR states which transports and profiles it migrated, adds its own
behavioural tests against the fixtures, and updates this document.

[QUALIFICATION.md](QUALIFICATION.md) is the final receipt (#29): the cross-path matrix,
the ownership of each acceptance item, the measured preparation cost and the live gates
that stay unproven.

## Contract fixtures and test helpers

`crates/cpa-exec/tests/fixtures/codex_contract/` holds small hand-authored payloads.
`manifest.json` records, for each one, the transport, the direction, the endpoint
profiles, the kind of evidence, the exact sources and the contract it shows. The
kinds of evidence are `first-party-source`, `first-party-test`, `provider-docs` and
`contract-probe`. A probe tests a contract rule and is never evidence of what a client
sends.

Follow these rules when you add a fixture:

- Write it by hand from the cited source, and cite file paths with line ranges at the
  pinned commit, or a documentation URL.
- Use placeholders only. No credentials, captured traffic, account IDs or real
  conversation content.
- Never generate a fixture by running this proxy or from a Go golden.
- Store the bytes as they appear on the wire. Do not pretty-print a payload whose
  spelling is part of the test.
- A fixture whose line ranges point at a researched first-party revision instead of the
  pin sets `revision` to one of the manifest's `research` commits, and its notes say it
  is source-refresh evidence that does not move the contract pin. Such a fixture shows
  what a newer client can send. It changes no rule in this document
  ([FP1-SOURCE-REFRESH.md](FP1-SOURCE-REFRESH.md)).

The test helpers are:

- `cpa_exec::codex_contract`, behind the `cpa-exec` feature `test-support`, which
  `cpa-server` enables for its tests. `fixture(name)` returns a fixture, `bytes()`
  returns its stored bytes, and `frames()` returns each WebSocket frame or SSE `data`
  payload as a slice of those bytes.
- `cpa_server::testing::codex_capture::CaptureUpstream`, a loopback upstream for route
  tests. It records each HTTP request body and each WebSocket text frame exactly as
  received, and answers from a `Script`.

The default test suite checks the fixture set and the helpers only. Each later PR adds
the behavioural assertions for the behaviour it implements.
