# Differences from Go CLIProxyAPI

This page is migration guidance for operators moving between CLIProxyAPI and cliproxy-rs. It lists the differences such an operator would notice in settings, credential files, routes, response shapes and the Management API, and known implementation limits. The comparisons name CLIProxyAPI v8.0.35, commit `ae3ee3be303fb07fb8173279923413005bf32177`, the last Go snapshot the fork was checked against. The page does not claim that every newer Go feature is ported, and it is not a ledger of every byte that differs from Go. Existing fixtures keep their original Go versions.

Codex JSON cleanup: request inspection no longer coerces a non-string
`prompt_cache_key` into header identity. The field still reaches the provider
unchanged, and the existing session fallback supplies the identity when available.
The pinned first-party `ResponsesApiRequest` models the cache key as
`Option<String>` (`codex-api/src/common.rs:305`), and the
[Codex contract](codex/CONTRACT.md#field-preservation) requires opaque field
preservation, not Go coercion. A non-string duplex frame `type` also no longer
becomes a name in its unsupported-type diagnostic; it is still refused locally.
Other providers keep their Go readers.
[The migration inventory](GJSON-MIGRATION.md) lists the remaining consumers.

## Compatibility policy

This fork keeps four built-in upstreams: Claude (`claude`), Codex (`codex`), Grok (`xai`) and Muse (`meta`). Functional behaviour is the contract: supported clients, configs and credential files keep working, and provider documentation, first-party clients and verified wire behaviour decide provider behaviour. Go CLIProxyAPI is a source, not an oracle. Go-compatible behaviour stays where a real client, an operator's config or a saved credential needs it, and Go goldens stay as regression fixtures. Go parser quirks and Go's exact wire output are not requirements on their own, and no Go comparison or benchmark gates a change ([#45](https://github.com/zakstak/cliproxy-rs/issues/45)). Codex follows its own [contract](codex/CONTRACT.md). A difference that an operator moving from Go would notice is listed on this page.

## Removed providers

Issue #49 removed these built-in integrations and their maintenance: Kimi (`kimi`, `kimi-ai`, `kimi.ai`, `kimi.com`), Devin, Gemini API keys and Gemini Interactions, Vertex AI, Google AI Studio, Antigravity, and the generic OpenAI-compatible upstreams (`openai-compatibility`, used for DeepSeek, GLM, OpenRouter and similar services). Go v8.0.35 has all of them. What the fork does instead:

- Client protocols: Anthropic Messages, OpenAI Chat Completions, Completions and Responses remain, with translation to all four upstreams. The Gemini (`/v1beta/models/...`), Gemini Interactions (`/v1beta/interactions`) and AI Studio relay (`/v1/ws`) routes answer `410 Gone` with a JSON error naming the supported providers, as do the `/antigravity/callback`, `/devin/callback` and `/callback` login callbacks. Go serves them.
- Configuration: a config that sets `api-keys.gemini`, `api-keys.interactions`, `api-keys.vertex` or `api-keys.openai-compatibility` (legacy `gemini-api-key`, `interactions-api-key`, `vertex-api-key`, `openai-compatibility`), `oauth.providers.antigravity`, `devin`, `aistudio` (legacy `ws-auth: true`), `kimi`, `gemini`, `gemini-cli` or `vertex`, `models.devin-catalog`, or a removed provider's entry under `oauth.model-alias`, `oauth.excluded-models`, `oauth.settings` or `oauth.request-scoped-errors` is refused with a message naming the setting and its legacy spelling, at startup, on a reload (the running config stays) and on a Management API write, which answers `422` and leaves the file as it was. That check comes before Go's own validation of the setting, so a write that also holds an invalid value for it (a malformed `devin-catalog` URL, a Gemini key weight out of range) gets the migration error where Go answered `400` or `422` with its validation error. An empty list, empty map, `false` or empty string is accepted, so a config that only carries Go's empty defaults still loads.
- Saved logins: auth files of a removed provider (`type` `kimi`, `devin`, `gemini`, `gemini-cli`, `vertex`, `aistudio`, `antigravity`, `openai-compatibility`, ...) stay on disk unchanged and are not loaded; each scan logs a warning naming the file. Nothing deletes or rewrites them, so the same `auth-dir` still works with Go.
- Command line: `-kimi-login`, `-kimi-ai-login`, `-antigravity-login`, `-devin-login` and `-vertex-import` are hidden and exit with an error that names the supported providers, without touching `auth-dir`.
- Management API: `/oauth/auth-url` and the v0 `*-auth-url` routes for Kimi, Antigravity and Devin, `/oauth/import?provider=vertex`, v0 `/vertex/import` and the v0 `gemini-api-key`, `interactions-api-key`, `vertex-api-key` and `openai-compatibility` lists answer `410 Gone` with top-level `code: "removed_provider"` and the guidance in the existing `error` string. Unknown providers stay `404 provider_not_found`. The TUI and the dashboard offer only the four providers; the dashboard no longer imports Vertex service accounts or reads Kimi and Devin quota.
- Model catalog: the embedded `models.json` is Go's without the `gemini`, `vertex`, `gemini-cli`, `aistudio`, `kimi` and `antigravity` sections, and lookups, validation and refresh change reports cover only the retained sections. A remote catalog may still carry the removed sections; they are ignored. The Devin catalog and its updater are gone, so a model that only those sections described gets no catalog capabilities, also when a Claude- or Codex-bound translation looks it up (for example `kimi-k2.5` on a Claude API key).
- Claude executor: Go's Kimi delegation is gone. A Claude API key whose base URL is Kimi's (`api.kimi.com`, `api.kimi.ai`) is an ordinary Claude-compatible upstream: its Claude Code attribution block is no longer stripped and its device identity seeds from the key.
- Codex translated route: it converts Claude Messages and Chat Completions; Gemini and Interactions sources are no longer clients.
- Home mode: a dispatched credential of an unsupported provider is refused (`executor not registered`); Go would run one with a base URL on its OpenAI-compatible executor.
- LAN discovery advertises the `chat-completions`, `responses` and `messages` protocols and no `api_gemini` path. The default `server.discovery.subtypes` (legacy `discovery.subtypes`, as the v0 config view shows it) is `_chat-completions`, `_responses`, `_messages`, without Go's `_generate-content` and `_interactions`. Without that record, a TXT set that reaches its size limit can keep a later record (such as `protocols`) that Go dropped, which can in turn leave out one Go kept (such as `node_role`).

## Additions in cliproxy-rs

- Routing strategy `soonest-reset` (alias `reset-first`): select the account whose weekly window resets soonest, until it cools down or reaches a limit, then move to the next. An account whose reset time is not known yet gets one probe request. Conversations bound to an account stay on it. Go has only `round-robin`, `weighted-round-robin` and `fill-first`, and reads `soonest-reset` as `round-robin`. The dashboard offers it only when it is connected to cliproxy-rs. See [MULTI-ACCOUNT.md](MULTI-ACCOUNT.md#routing-strategies).
- Default routing strategy: an unset or empty `routing.strategy` is `soonest-reset`; Go reads it as `round-robin`. Accounts without reset headers, such as API keys, take turns as with `round-robin` once each has had its one probe request (so the first requests of each model can go to a different key than in Go), and with several providers for one model the first provider serves until none of its accounts is ready, where Go rotates across the providers. `GET /v0/management/routing/strategy` answers the effective `soonest-reset` for an unset strategy (Go answers `round-robin`) and writes nothing; the config reads show the file as it is, without the key. The TUI and the web dashboard show the effective strategy the server reports, `round-robin` when connected to Go. `PUT` with an empty value writes `round-robin`, as in Go. An explicit `round-robin`, `fill-first` or `weighted-round-robin` behaves as before.
- Codex connection reuse, on by default ([#147](https://github.com/zakstak/cliproxy-rs/issues/147)): the Codex client for `chatgpt.com` keeps up to 2 idle connections per host and proxy for 90 seconds and sends later ordinary requests on them, several at once over HTTP/2. Go v8.0.35 dials a dedicated connection for every request and closes it with the response body (`helps/utls_client.go`). Reuse changes no request byte, header, ClientHello or proxy, connections never cross proxies, and no retry is added: a request that a pooled connection lost after writing it fails and does not fail over ([CONTRACT.md](codex/CONTRACT.md#http-connection-reuse)). Gated requests, those under a client authority (N1 #111), still dial a dedicated connection whatever the setting. `oauth.providers.codex.chatgpt-keep-alive: false` restores Go's connection per request. An absent or null key means on, and a Management API write of null saves `true`. The setting applies from the next request after a config reload. Turning it off closes the pooled connections at the next Codex HTTP request on any route; without one they close at the idle timeout. Go starts with the key in the file and ignores it. A config edit through Go's v8 Management API moves the key into a comment, so an explicit `false` no longer applies when you return to cliproxy-rs and reuse is on again. Edits through Go's v0 endpoints keep the key. Setting the key through Go's v8 API is refused, as for any key Go does not know. Until #147 the key was off by default.

- Usage record additions: each record in the usage queue (`GET /v0/management/usage-queue`, `GET /v8/management/observability/usage/queue` and the RESP `usage` channel) gains, after Go's fields, `session_source`, `prompt_prefix_hash`, a `timings` object and three byte counts, to show which conversation a request belongs to and where the time to the first token goes. Go's `session_id` is already the conversation: the session key the server derives for every request, whether or not `routing.session-affinity` is on, as a UUID (a client's UUID as sent, anything else hashed). `session_source` says where that key came from: `header` (a client session header such as `X-Claude-Code-Session-Id`), `metadata` (a session in Claude's `metadata.user_id`), `user_id` (a plain `metadata.user_id`, which names a user rather than one conversation), `body` (another body field such as `prompt_cache_key` or `conversation_id`), `execution` (a Responses WebSocket session), `derived` (no session signal: a hash of the leading instructions and the first user input, so it changes with the system prompt), `messages` (the first-messages hash), `lcp` or `home` (the session that session affinity or Home bound the attempt to). `prompt_prefix_hash` is 16 hex digits, the first 64 bits of a SHA-256 over the client's `tools` and system prompt (`system` for Messages, `instructions` for Responses; none for other formats) as the route passed them on, before plugin interceptors, translation and cloaking, `cache_control` markers included (the Messages route passes them on as sent; the Responses routes may first have rewritten a Codex client's multi-agent tools), so another mode or a subagent shows as another value; no prompt text is recorded. Claude attempts also add `claude_cache`: final upstream TTLs, hashes and byte sizes of the serialized fingerprint input, hashed session and account scope, request kinds, and absolute attempt timestamps. Returned five-minute and one-hour cache-write buckets appear in `tokens` only when Anthropic supplies them. See [Claude cache telemetry](CLAUDE-CACHE-TELEMETRY.md) for the schema and offline replay limits. `timings` holds milliseconds since the server accepted the client request: `client_body_received_ms` (the request body was read to its end), `upstream_started_ms` (the upstream request is about to be sent), `upstream_connected_ms` (the HTTP client has a connection and starts writing the request), `upstream_connection_reused` (`true` when the request went out on a pooled connection; left out when a connection was dialled while it waited, since the client may still have used a pooled one that came free first and does not say which), `upstream_body_sent_ms` (the client took the last of the body into its write buffer: handed over, not acknowledged by the upstream: the client takes another 64 KiB piece while its buffer holds less than 408 KiB, so under 472 KiB of the body plus what the kernel's socket buffer holds may still be on its way), `upstream_headers_ms` (the response head arrived), `upstream_first_byte_ms` (the first response body bytes arrived) and `client_first_byte_ms` (the request's first response bytes were handed to the client's connection before the record was published: a stream's first event, or a keep-alive sent while a buffered response waited; a buffered response without one publishes its record before its body is written and leaves it out). `client_request_bytes`, `upstream_request_bytes` and `upstream_response_bytes` (as received, before content decoding) follow. A field that was not seen is left out. The Claude executor fills them all; other executors leave out the upstream fields. `upstream_connected_ms` and `upstream_body_sent_ms` are reported only where the upstream speaks HTTP/1.1: `api.anthropic.com` and plain `http://` base URLs. A Responses WebSocket turn counts from the start of the turn and has neither the client body fields nor `client_first_byte_ms`. A record covers one upstream attempt, so a retried request's later attempts show when they started. When the upstream redirects, the upload fields describe the last request sent: a redirect followed as a GET has `upstream_request_bytes` 0 and no upload times, and a hop that is not timed leaves them out. While usage statistics are on, a request body goes to such an HTTP/1.1 upstream in 64 KiB pieces instead of one, with the same bytes and `Content-Length`. Go's record has none of these fields; readers that ignore unknown fields are unaffected, and usage plugins get Go's record unchanged.
- Live usage feed for the dashboard: `GET /v8/management/observability/usage/live?after=<cursor>&count=<n>` (management key required) returns `{"cursor", "gap", "more", "usage_statistics_enabled", "records"}`. `records` holds the same usage records as the queue, byte for byte, and reading them removes nothing, so the queue, its v0 alias, RESP `usage` subscribers and other readers are unaffected. `cursor` is an opaque string that names this process's feed and a position in it; pass it back as `after`, and anything that is not such a cursor gets 400. Without `after`, the answer only gives the current cursor. A page holds at most 500 records. The server keeps one shared copy of at most 2,000 records and 8 MiB (plus the newest record), keeps no state per reader, and keeps records only while someone read the feed in the last 60 seconds. `gap` is `true` when records after the reader's cursor are gone: evicted, recorded while nobody read the feed, or the cursor came from another process (a restarted server), in which case the reader gets every kept record. Go has no such route; its dashboard reads the destructive queue.
- Codex WebSocket transport causes in the request log: an `api.websocket.error` event for a failed dial, read or write gains a `Cause:` line after Go's `Error:` line, such as `Cause: connect (ConnectionRefused): ...`, `Cause: tls: ...`, `Cause: remote_close: code 1011`, `Cause: eof: the stream ended without a close frame` or `Cause: local_timeout: no application message within 300s`. The first word comes only from typed evidence (the HTTP client's DNS, proxy, TLS, timeout or connect classification, a BoringSSL error, an OS error kind, a WebSocket protocol error, the permessage-deflate layer, or the proxy's own handshake, idle or write timer); anything else is `unclassified`, followed by the library's text. Go returns the library error itself to the client and logs it unchanged; cliproxy-rs keeps its fixed client texts (`codex websockets executor: dial failed`, `read failed`, `write failed`, gorilla's close 1006 text for a stream that ended) and their status, scope and retry handling, and writes the cause only to the request log. Before writing it, the log escapes control characters and whitespace other than a space, keeps only a URL's scheme, host and path, and redacts credential fields whatever their length or spacing: after a credential-like name (`authorization`, `cookie`, `key`, `token`, `secret`, `password`, ...) or an auth scheme followed by `:`, as in a header line or JSON, everything to the end of the cause; after `name=`, a single bounded value, or everything to the end when the value is empty, quoted across a space or an auth scheme; the word after a standalone `Bearer`, `Basic` or similar scheme, and everything after `Digest`. Redaction happens before the cut to 1 KiB. A secret with no such marker in a library text is not recognised. xAI WebSocket errors have no `Cause:` line yet.
- `worker-threads` (top level of `config.yaml`): the number of request threads, by default the smaller of the CPU count and two; see [CONFIGURATION.md](CONFIGURATION.md#worker-threads). Go sizes its scheduler by the CPU count. The key is read once at start from the `-config` file (`./config.yaml` by default), before a remote store or Home supplies a config; in a store's `config.yaml` or in the config Home supplies (the local `-config` file still applies) it has no effect, and those deployments set `TOKIO_WORKER_THREADS` instead. Go starts with the key present and keeps it through v0 Management API saves. Any v8 configuration write (PUT, PATCH or DELETE under `/v8/management/config`) turns it into a `# worker-threads: N` comment and logs `unrecognized configuration section "worker-threads" commented out during v8 migration`, and `PUT /v8/management/config.yaml` with the key answers `unknown v8 configuration section worker-threads`. When one config.yaml is shared with a Go server, set `TOKIO_WORKER_THREADS` instead.
- GPT Image 2.6 on Codex, a forward port: `gpt-image-2.6-flare` (GPT Image 2.6 Flare) and `gpt-image-2.6-sunburst` (GPT Image 2.6 Sunburst) are Codex built-ins next to GPT Image 2.5. They follow the same registration and exclusion rules, are accepted on `/v1/images/generations` and `/v1/images/edits` through the direct Images endpoints, appear after `gpt-image-2.5` in the supported-model error, are refused on text routes such as Chat Completions and Responses as image-only models, and are hidden in the Codex client catalog. There is no bare `gpt-image-2.6`. Go v8.0.35 rejects both IDs on the image routes and does not list them. The change follows [CLIProxyAPI PR #7261](https://github.com/router-for-me/CLIProxyAPI/pull/7261) at `4d5658e43c5559c18a3b587a247c0f224512be00`, which was still open when ported. Tests that compare against Go goldens add the two models to Go's recorded model lists and error message (`crates/cpa-server/tests/forward_port`). Local tests use mock upstreams only. The live generation reported in the PR is upstream evidence and was not reproduced with cliproxy-rs.
- Retained model catalog additions ([#68](https://github.com/zakstak/cliproxy-rs/issues/68)): the embedded `models.json`, the catalog in effect until a remote catalog is read, gains three models that Go v8.0.35 lacks. Every existing entry stays, `gpt-5.5` included; Go v8.0.67 drops `gpt-5.5` from its static Codex tiers, and that removal is not ported. `claude-fable-5-2` (Claude Fable 5.2) follows `claude-fable-5-1`: 1,000,000-token context, 128,000 output tokens, text and image in, text out, thinking that cannot be turned off, and `low` to `max` effort, from Anthropic's models overview, Fable 5.2 page and effort page (retrieved 2026-11-12; released 2026-11-09), with the model ID also in the Claude Code 2.1.321 changelog. Its description is Anthropic's; Go v8.0.67 (`19a0a854`) reuses Fable 5.1's text, which states Fable 5's prices, while Fable 5.2 costs $8/$40 per million tokens where Fable 5 costs $10/$50. `gpt-6.1-terra` (GPT 6.1 Terra) follows `gpt-6.1-sol` in `codex-team`, `codex-plus` and `codex-pro` and follows `gpt-6-luna` in `codex-free`, from the first-party openai/codex `models-manager/models.json`, identical at the contract pin `44ccf394573c` and at `5c3ff1dabf64`: 500,000-token context, text and image in, native web search (`supports_search_tool`) and configuration updates (`supports_reasoning_effort_updates`; a Codex API key still turns them off, as for every Codex model), `low` to `max` effort, and that file's description. That file lists Terra for every plan these four tiers stand for; a static list is not proof that an account may use the model. It states no maximum output, so the entry has no `max_completion_tokens` where Go's has 128,000; the Claude-format model list therefore shows its 64,000 default for Terra. It also lists an `ultra` effort, which, as for the other GPT-6 entries, the catalog does not carry because cliproxy-rs has no `ultra` thinking level. `muse-ember-1.0` (Muse Ember 1.0) comes first in `meta`, from Meta's Muse Ember and reasoning pages at dev.meta.ai (retrieved 2026-11-12): 1,048,576-token context, 524,288 output tokens, text, image, video and audio in, text out, `minimal` to `max` effort, and no contributor variant. Unlike Go's entry it claims no native web search, which the Meta route does not read; Meta documents search grounding, not that a Responses `web_search` tool reaches Muse. One Go v8.0.67 candidate is left out: `gpt-6-chat-thinking`, which no first-party Codex source lists and which Go describes as a paid experiment. `grok-imagine-video-1.5-lite` is not a catalog entry here: X4 ([#87](https://github.com/zakstak/cliproxy-rs/issues/87)) adds it as an xAI built-in together with the video route that accepts it (see "Grok Imagine Video 1.5 Lite"). A remote catalog that is read, credential exclusions, aliases, prefixes and configured model lists still decide what is registered. Request handling for the new models is unchanged: Fable 5.2 gets no Fable 5.1-specific Claude gates (C1, [#69](https://github.com/zakstak/cliproxy-rs/issues/69)), and Muse Ember gets no new identity headers (M1). The Go goldens compare with these additions applied (`crates/cpa-server/tests/forward_port/mod.rs`, `k1_catalog`).
- On-demand model catalog refresh ([#98](https://github.com/zakstak/cliproxy-rs/issues/98)), a forward port of Go CLIProxyAPI `10417e5b` (after v8.0.35): `POST /v8/management/routing/model-definitions/refresh` and `POST /v8/management/models/refresh` (management key required) read models.json and the Codex client catalog from their current sources once, now, and publish them as the three-hourly read would. The sources are the ones the running updaters use, so `--local-model`, Home mode and `disabled` apply: a catalog whose source is `embed` or `disabled` is skipped and nothing is read. The answer is Go's: `ok`, `status`, `catalog`, `codex_catalog`, `sources`, `catalogs` (each with `source`, `refreshed`, `skipped`, `changed_providers` and `error`) and `changed_providers`, with 200 when every catalog was read or skipped, 502 when one failed and 400 for invalid sources. A failed catalog keeps its last valid data. `changed_providers` names the retained providers whose models.json section changed (`claude`, `codex`, `xai`, `meta`); the Codex client catalog reports none, as in Go. These parts differ from that Go commit:
  - Go's `devin_catalog` members, and the Devin catalog itself, are left out with the removed provider (issue #49).
  - Concurrent requests for the same source share one read, and the read runs on even if the request that started it goes away. Go starts one read per request.
  - One read is bounded to 65 seconds, enough for both default sources at their 30-second bound. Go bounds it only by the request.
  - Every read, periodic or on demand, takes a sequence number when it starts, and publishes only while its source is current and no read that started later has published. Go `10417e5b` fences the same way. A read whose source changed answers `model catalog source changed during refresh`, as in Go.
  - Other error texts are cliproxy-rs's: `model catalog refresh timed out`, `model catalog updaters stopped` (the runtime is shutting down), `model catalog rejected; keeping last valid catalog` and `model catalog refresh ended without a result`. Go returns the context error or the decoder's text.
  - A `GET` of `.../model-definitions/refresh` still reads the `refresh` channel (`400 unknown channel`), as gin's `GET :channel` route does. Only `POST` refreshes.
  - A runtime whose updaters were never started reads the sources its current config resolves to, as Go falls back to the handler's config. Home mode is known only once the updaters start, so this fallback does not apply it. `cliproxy` always starts them. Fallback reads capture the config revision with the source, and publication holds the config commit lock. Any intervening config commit invalidates the read, even when the source URL stays the same. A request after that commit starts a new read instead of joining the invalidated one.
- Bounded cooldowns and model listings ([#98](https://github.com/zakstak/cliproxy-rs/issues/98), Go CLIProxyAPI `69ed202a`): when `routing.cooldown.max-trusted-cooldown` cuts a stated quota reset, the credential's models come back in `/v1/models` once the bound ends, in the same process, while the stated reset is still ahead. Listings compare cooldown deadlines with the current time on every request, so no timer or restart is involved. A regression test covers it; no code changed.

Claude cache observations require the separate default-off
`observability.usage.claude-cache-telemetry` opt-in as well as usage statistics.
The `bytes` values measure serialized fingerprint input, including path and role
strings and tuple JSON framing, not raw section lengths or token counts. Claude
cache telemetry hashes use a private random process-local HMAC key and rotate
on restart, including identities derived from configured API keys.

The queue and RESP channel gain additional zero-token observations marked
`usage_observed: false` on `Ending::Done` (completion or client drop) only when
all these conditions hold:

- The attempt was not discarded and has not already been published.
- The executor has not published an outcome.
- The executor marked the attempt as usage-required, but no usage was observed.
- Collected Claude telemetry is present, requiring the telemetry opt-in and usage
  collection to be enabled.
- The usage queue accepts records (management and usage statistics are enabled).

Go emits no record on this no-usage path. The additional records' zeros mean
unknown usage, and `failed: false` does not establish success. Failed attempts do
not receive this marker.
A native non-streaming Claude JSON response without usage still publishes an
ordinary record through its executor-supplied outcome, without this marker.
Absence of the marker therefore does not prove that usage was observed.
Ordinary records keep Go's accounting.

## Deliberate differences

- Response header field-name case and order: cliproxy-rs writes downstream response header names in lowercase, in the order the handler sets them (for example `content-type`, `x-cpa-trace-id`, then the CORS fields). Go's `net/http` writes canonical-case names (`Content-Type`) sorted by name. HTTP field names are case-insensitive and the order of different field names carries no meaning (RFC 9110 sections 5.1 and 5.3), so field values and bodies are unchanged; only a client that compares raw header bytes sees a difference. Upstream request headers are unaffected: each provider's client profile keeps its own case and order. The retired Go differential harness ([archive](../harness/README.md)) named this `downstream-header-framing` and still compared every field value.
- Supported hosts (this fork, zakstak/cliproxy-rs): the proxy builds and runs only on Linux, natively or in the Linux container. Go and upstream cliproxy-rs also build for Windows and macOS. Here a build for any target other than `target_os = "linux"` stops with a `compile_error!` in `cpa-core` that points to the container. There are no Windows or macOS release archives, installers, packages, file watchers, idle gates or CI jobs. On those systems, run the container ([INSTALL.md](INSTALL.md#windows-and-macos-run-the-linux-container)). Clients on Windows and macOS connect to the proxy as before. Config files, credential files, routes, client identities and the Management API do not change. Go behaviour that exists only on Windows or macOS hosts, such as Windows plugin loading, Windows file locks and paths, and macOS kqueue file events, is out of scope.
- Models of credentials with another provider: a credential whose provider is none of `claude`, `codex`, `xai` and `meta`, such as a Home-dispatched auth of provider `zed`, registers no models, and a `provider_key` or `compat_name` attribute doesn't change that. Go registers it as an OpenAI-compatible credential: the models of the `openai-compatibility` entry named like the provider (case-folded), if any, under its lowercased `provider_key` (`Foo` registers under `foo`), or under the provider without one. That executor was removed (see [Removed providers](#removed-providers)).
- Native plugins ([#47](https://github.com/zakstak/cliproxy-rs/issues/47)): this fork has no Go-compatible native plugin support. It loads no plugin libraries (C ABI 1, registration schema 6) and runs no plugin hooks: frontend auth providers, model routers, plugin catalogs and executors, schedulers, request translators and normalizers, thinking appliers, request, response, stream-chunk and model-list interceptors, WebSocket response observers, request lifecycle and usage plugins, auth providers (`auth.parse`, plugin refresh, plugin-virtual credentials) and the `host.*` callbacks. It has no plugin store, no plugin command-line flags and no Home-managed plugin sync, tasks or status reports. A config with a `plugins` section, in any layout and whatever it holds (`plugins: {enabled: false}` included), fails to load with an error that names the section and points to [MIGRATING-FROM-GO.md](MIGRATING-FROM-GO.md#native-plugins); a reload with one keeps the running config, a Home config with one is refused and fetched again, and a Management API write that would add one is refused with `422 invalid_config`. A flag a plugin used to add is an unknown flag. The plugin, plugin store and plugin quota routes (`/v8/management/plugins...`, `/v0/management/plugins...`, `/v0/management/plugin-store...`, `/v0/management/quota/...`) answer `410` with `{"error":"plugins_removed"}` behind the management guard, and `/v0/resource/plugins/...` answers the same without it; the top-level `quota_probe` credential metadata that `quota/fetch` ran is refused for any value, including `null` and `false`. Local scans skip the credential with a migration warning, uploads and field edits return `400` before changing the file, and Home dispatch refuses the credential. The error names `quota_probe` and directs operators to `requests/api-call` with `$TOKEN$`. Management responses carry `X-CPA-SUPPORT-PLUGIN: 0`, as Go's builds without cgo do, the v0 config view has no `plugins` section, and the dashboard has no plugin page or plugin quota and sign-in options. Credential files are left as they are: a file of a type only a plugin parsed loads with the built-in reading, and no built-in executor serves it. Go v8.0.35 recordings that contain plugin cases are kept as historical evidence; the tests that replay them drop those cases or expect the refusal.

- Codex request boundary: a Responses body bound for a Codex credential, from a Responses client on HTTP streaming, buffered, compact or a WebSocket turn, is refused with a 400 request error before anything is sent upstream when it is not UTF-8, is not valid JSON (including content after the root value and a lone surrogate escape), repeats a key in any object (compared after unescaping), nests more than 100 levels, is not an object, or has a `model` that is not a string, a `stream` that is not a boolean or a `previous_response_id` that is neither a string nor null. Through the server, a body over 64 MiB meets the shared request limit first (see "Request body limits": a 400, or Go's 413 under a configured limit); only a caller of the executor that skips the server gets the boundary's 413. Go reads such bodies with gjson, which takes one of the repeated keys, ignores trailing content and coerces types, and sends whatever its rewrites produce. The error names a byte offset or a field, never body content. Valid bodies, including unknown fields and numbers outside the float range, pass unchanged; the other Codex entries below still apply to them. Bodies from Chat Completions, Claude and Gemini clients keep Go's parsing. A local token count of a Responses body applies the same rules. The Images API on a Codex model applies them to the client's JSON on both of its paths, with its own member types instead of the Responses ones. A malformed body gets this 400 where Go answers `invalid OpenAI image generation request JSON` with a 500. The Images handler applies these rules to a Codex model's original body before it rewrites `model` and `stream`: a non-boolean `stream` is refused, where Go reads `"true"` or `1` as `true`, and so is a repeated `stream` or `model`, where Go reads the first and its `stream` deletion can leave the other for the adapter. A `prompt`, image setting, `response_format` or image reference that is not a string, and an `n`, `output_compression` or `partial_images` that is not a number, are refused, where Go reads them as text or a number, drops a count that is not a number and truncates one that is not whole. The tool request copies a count with its number spelling. In a multipart edit on a Codex model, a text field that is not UTF-8 is refused, where Go replaces the bad bytes with U+FFFD; `model` or `stream` sent twice is refused on both paths, and any text field sent twice on the tool path, where Go reads the first; a `stream` that is not one of Go's boolean spellings (`true`, `1`, `yes`, `on`, `false`, `0`, `no`, `off`, ASCII case and white space ignored, empty as false) is refused, where Go reads it as false; on the tool path, an `output_compression` or `partial_images` that is not a decimal integer in the `i64` range is refused, where Go leaves it out and the provider default applies, and `n` must be exactly one by its decimal digits, where Go compares a float, so `1.0000000000000001` passed as one image; and the direct path preserves literal field names, including whitespace and editor metacharacters, and recognizes the count fields `n`, `output_compression` and `partial_images` by their exact names, where Go trims or lowercases names first. Text in a padded routing field is still checked as UTF-8 before any field is discarded. The Responses Lite marker (the `x-openai-internal-codex-responses-lite` header and its `client_metadata` member), which selects the Lite and session headers a native WebSocket handshake forwards, is trimmed of ASCII white space only, where Go also trims Unicode spaces such as U+00A0. [codex/CONTRACT.md](codex/CONTRACT.md#request-boundary) has the full policy.

- Payload rule parameter order: one `default`, `default-raw` or `override` rule that adds several new keys adds them in the order the config lists them. Go keeps a rule's `params` in a Go map, whose iteration order is random, so the same request can reach the upstream with those keys in a different order from one request to the next. The values and the set of keys are the same. Likewise, an images multipart form that the rules changed is rebuilt with its parts in the order of the rules' JSON result; Go writes them in random order.
- Payload rule paths: cliproxy-rs applies only paths its JSON port reads exactly as Go's gjson does. Those are dot- or pipe-separated plain keys and indexes, with `\` escapes and `*`/`?` wildcards; a bare `#` (a count, or `#.key`); `@this` without arguments; and whole `#(query)` or `#(query)#` parts whose predicate has no `@`, no `|` and no nested query, and in which each `&&`/`||` term is one query whose path is itself in this set. A parameter with any other path is dropped after Go's whole-rule check of raw values, so an invalid raw value still drops its whole rule. A model entry whose `match`, `not-match`, `exist` or `not-exist` path is outside that set never matches. Examples are subselectors (`[a]`, `{a}`), modifiers other than `@this`, `@this` with arguments, static values (`!true`), JSON lines (`..`), `#[...]`, queries after a pipe or with `@` or `|` in the predicate, and quotes or parentheses in a plain key. Go reads these with gjson, and its edits go through sjson, which parses the same path differently. Its results vary: `[a].#(k==1)#.x` changes nothing, an `@reverse` override changes nothing but marks the path as applied, an `exist: ["{a}"]` condition holds for any object body, and `not-exist: ["a(|@reverse"]` holds when the key `a(` is missing.
- sjson deletion of escaped keys ([#146](https://github.com/zakstak/cliproxy-rs/issues/146)): deleting a member whose key holds an escaped quote removes the whole member, so a `requests.payload.filter` param `\"x` turns `{"\"x":1,"y":2}` into `{"y":2}`. sjson v1.2.5, which Go's payload rules and translators use, misreads the key's opening quote and leaves `{"\"x":,"y":2}`, which is not JSON. The fix is in the shared deletion (`cpa_common::json::try_delete`, `delete`, `delete_changed`), so every caller gets it; other bytes of the document are kept as they were. The recorded Go vector stays in `crates/cpa-common/tests/fixtures/sjson_go_vectors.json`, and the test lists this case as a difference.
- Bounded JSON walks ([#146](https://github.com/zakstak/cliproxy-rs/issues/146)): translators walk nested JSON with their open containers on the heap, on the caller's thread, and descend at most 128 levels (`cpa_common::json::WALK_DEPTH_LIMIT`) from where each walk starts. Go's walkers recurse to any depth on growable goroutine stacks and rescan each level's subtree, which costs time quadratic in the depth. Below 128 levels the output is Go's. Deeper than that:
  - A value converted through gjson's `Result.Value()` model (Claude tool `input_schema` sent to Chat Completions, Chat tool calls, Responses JSON schema fields and tools) keeps a deeper container as its source bytes when it is valid JSON: member order, spacing and escaping as received, where Go sorts keys and re-escapes. An invalid deeper container becomes `null`.
  - Schema normalization (object `properties`, unsupported regex escapes, `true` subschemas) does not reach those raw containers. Codex's missing-`required` check does not inspect deeper subschemas.
  - Responses namespaces and nested `tool_choice` tools deeper than the limit keep their bytes, without the apply_patch rewrite. Function names declared in deeper nested `tools` lists are not collected for name sanitizing, and deeper nested `reasoning_details` arrays add no reasoning text.
  - Dialect-keyword stripping for Codex tool parameters decodes with encoding/json's limit of 10000 levels and then walks every level, as Go does.
  - A gjson or sjson path with more than 128 components (separated by `.` or `|` that is not escaped) reads as not found, and an edit by that path fails with `path has more than 128 components` and leaves the document unchanged. Go descends one level per component without a limit. No translator builds such a path; a configured payload rule with one has no effect.

  The removed workaround estimated nesting from every `{` and `[` in strings, counted across a whole stream, and ran each translation over 256 levels on a new thread with an 8 MiB to 1 GiB stack; code in text deltas started one thread per stream event, and a failed stack reservation ended the request with a `translator: cannot reserve a ... stack` error. That error no longer exists. Session-ID derivation walks a request's user content on the heap too, so content nested up to encoding/json's 10000 levels no longer overflows a server thread. xAI `$ref` inlining (`cpa_common::schema_refs`) still runs on its own large-stack thread per schema that holds a `$ref`; it is per request, not per event.
- Token counts and the payload rule baseline: on the Claude and Codex `count_tokens` paths, a client's original request that fails to translate (for example a Claude user turn whose only block is a `container_upload` file source, which Gemini cannot inline) refuses the count with that translation error, whether or not any payload rule is configured. Go keeps the partial body its translator returns alongside the error and checks `default` and `default-raw` rules against it, so the count proceeds and a default the client already set is not added. cliproxy-rs has no partial body to check against, and an empty baseline would add the default.
- Codex `response.interrupt` acknowledgements (current Codex, not v8.0.35): Codex `e0aa043` sends `response.interrupt` for a response it cancels and then waits, up to one second, for both the response's terminal event and a `response.interrupt.accepted` or `.failed` with the same `response_id`, in either order; without the acknowledgement it retires the connection. Go v8.0.35 predates that handshake. cliproxy-rs keeps it:
  - A Codex WebSocket turn that forwarded an interrupt keeps reading after the response's terminal event until upstream's acknowledgement for that response arrives, then passes it on unchanged and ends; Go ends the turn at the terminal event and drops later frames. The wait is bounded at one second, Codex's own deadline; when it runs out or the socket fails, the turn ends without an error and the next turn proceeds. On a steering stream, which does not end at a terminal event, acknowledgements pass through as before.
  - An acknowledgement whose `response_id` no forwarded interrupt named, or one that arrives after its wait ended, is dropped instead of reaching the client: Codex fails a response on an acknowledgement for another response ID. Go forwards whatever arrives while a turn reads.
  - An interrupt for a response the socket already finished goes upstream when no later turn is reading on the socket (Go answers success and sends nothing), and upstream's acknowledgement, if one arrives within one second, is sent to the client. If the socket closes meanwhile, the client gets the loss as a 400 error event; if the session's credential is disabled, the client gets the usual `websocket credential is no longer enabled` error. While a later turn reads on the socket, such an interrupt is still answered with nothing and not forwarded, as in Go. On a steering stream, an interrupt for any response of the stream goes upstream.
  - An HTTP turn ended by a local interrupt sends `{"type":"response.interrupt.accepted","response_id":…}` before its interrupted `response.incomplete`, with the interrupt's `response_id`; the proxy itself cancels that turn. An interrupt for the response the connection's last turn finished, with no turn in flight, gets the same acknowledgement instead of the `no active upstream websocket for response.interrupt` error Go sends; an interrupt that reaches an HTTP turn after its terminal event was sent gets only the acknowledgement, not a second terminal event.
- Codex empty incomplete responses: in Go (`IsCodexTerminalEmptyIncomplete`), a `response.incomplete` with no output items, no output delta and `usage.output_tokens` 0 is an upstream silent abort. Go answers it with a request-scoped 502 and, on a WebSocket, drops the socket. On the native Codex routes (HTTP streaming and buffered answers, ordinary WebSocket turns, steering connections and WebSocket turns over HTTP), cliproxy-rs replaces no `response.incomplete`, whatever its reason, output or usage, and whether or not anything was delivered before it. The client gets the event as sent: a buffered client gets its `response` object under HTTP 200. A WebSocket keeps its socket, the credential does not cool, and passive accounting records the response as it records any terminal event the provider sends, where Go recorded the 502 as a failure. Per docs/codex/CONTRACT.md "Permitted transformations", the pinned Codex client classifies the event itself (`codex-api/src/sse/responses.rs:451-506` at 44ccf394573c). `interrupted` ends the turn, `content_filter` is its own error, and any other reason, `unknown` when missing, is a terminal `ResponseIncomplete` with its ID, usage and partial output and no retry delay (`protocol/src/error.rs:428-442`). The 502 would replace that with a proxy error. A stream or socket that ends without any terminal event still fails, as in Go (a request-scoped 408 on HTTP), and no terminal event is invented for it. The translated route (Claude Messages and Chat Completions into Codex) keeps Go's rule until #27, except that, unlike Go, it exempts the reasons `interrupted`, `content_filter` and `max_output_tokens`.
- Codex credential isolation (#25 acceptance criterion 7, docs/codex/CONTRACT.md "Credential isolation"): on the native Codex routes (HTTP streaming, buffered and compaction answers, ordinary WebSocket turns with and without bootstrap buffering, steering connections and WebSocket turns over HTTP), nothing the proxy delivers carries an authentication value that the upstream request or socket that produced it carried: the `Authorization` credential, a cookie value, an API-key header or a URL password. Go forwards an upstream frame, error body, close reason or header that quotes the bearer token as it arrived. cliproxy-rs checks the original bytes (escaped spellings, private raw values, repeated members, arrays and invalid JSON included) against the values of that request, or of the handshake of the socket that read the frame, and of no other credential. A frame that carries one is not delivered and the response goes on as processed; a WebSocket turn or steering connection whose ending event or later failure carries one ends with a silent close. A failure that carries one keeps its classified status, cooldown and record, but its client gets a silent close (WebSocket) or an error rendered from the status alone (HTTP), never the upstream body, frame, subscription-limit event, close reason or passthrough headers, and a cooldown it starts shows only its status as the later "last error". A buffered or compaction answer that carries one fails with a request-scoped 502 that neither fails over nor cools, and its record is a failure without tokens. A frame without such a value keeps every byte. A withheld frame was still served, so the stream commits on it, also when a steering connection's duplex is the one that leaves it out: a response whose every frame is withheld, its terminal event included, keeps its processed outcome (one execution, a successful record with the reported usage, no cooldown) and is not Go's `empty_stream`, which would cool the credential and run the request again on another one. Go's request log and usage record keep an upstream answer as it arrived; cliproxy-rs scrubs the same values, bound to the same request or socket, from every log section, spool file, WebSocket timeline entry and every text of the upstream's answer a record keeps (`fail.body`, `response_headers`, `response_model`, `response_service_tier`) before they are kept, for every record of the connection, whichever publishes first (`[REDACTED]`, or the entry's length alone for an escaped spelling). Other record fields, the request body (the client's own bytes) and other providers' logs are unchanged.
- Codex pinned account failures on the native WebSocket routes (#6, docs/codex/CONTRACT.md "Responses and failures"): a `response.failed` or `error` frame whose error is a pinned Codex account kind (`RateLimitExceeded`: `rate_limit_exceeded`, `slow_down`; `QuotaExceeded`: `insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded`; `UsageNotIncluded`: `usage_not_included`; or the types `usage_limit_reached`, `usage_not_included`, `insufficient_quota`) never reaches a native WebSocket client as sent, whatever status Go's table gives it. Go's table classifies `slow_down` and `insufficient_quota` in a `response.failed` as 502 and delivers the frame. cliproxy-rs keeps that classification for the scheduler (status, cooldown, failover and record are unchanged) and withholds the frame, as it does for any account failure. The native HTTP route delivers it as before.
- Codex upstream event boundary: Go reads an upstream Codex event's `type` and failure fields with gjson, which takes the first of a repeated key and reads invalid JSON as far as it goes. An event that is not valid JSON, or whose `type` repeats, can therefore end a Go response, fail it, convert a context-window error or feed usage. On the native Codex routes (HTTP streaming and buffered answers, ordinary WebSocket turns, steering connections and WebSocket turns over HTTP), cliproxy-rs acts only on an event the pinned Codex client decodes as `ResponsesStreamEvent` (docs/codex/CONTRACT.md "Native HTTP route"). An event that client skips (invalid JSON, a repeated known member such as `type` or `response`, a known member of the wrong type) reaches the client as sent, and the stream goes on to the next event, where Go could cut the response short at it with a 502 or a converted failure. The decision includes the first-party build's serde_json `arbitrary_precision` and `raw_value` reading of an object whose first key is serde_json's private number or raw-value token, which refuses such an object unless it holds exactly that one valid value. A decoded event ends the response only when the pinned reader ends it: a `response.completed` without a `response` (missing or `null`) and a `response.done` pass as sent and end nothing, and usage skips them, where Go ends the response on either and records the usage of the first. Over HTTP (streaming and buffered), a `response.completed` or interrupted `response.incomplete` whose `response` the pinned client cannot read as `ResponseCompleted` (no string `id`, a malformed `usage`, `usage_metadata` or `end_turn`), and a content-filter `response.incomplete`, are processing errors its SSE reader records and reads past (`sse/responses.rs:677-690` at 44ccf394573c): cliproxy-rs forwards such an event as sent and keeps reading, so a later terminal event ends the response, is the buffered answer and supplies the usage, where Go ends on the first and records its usage. When the upstream ends cleanly after such an event with no later terminal event, the response ends on it as before (the buffered answer is its `response` object, the record its usage, not failed). When the body instead breaks with a read failure before any terminal event, the answer fails: a buffered client gets the request-scoped 408 of a stream without a terminal event and a streaming client the read failure, each with a failed record that carries no tokens, as every failure record does. On WebSocket turns, including turns served over HTTP, the turn still ends on such an event, because the pinned WebSocket reader returns that error and retires its socket. A failure is classified as the pinned `serde_json::Value` holds it, with the last of a repeated key (Go's gjson takes the first) and with serde_json's private number and raw value resolved (`{"error":{"$serde_json::private::RawValue":"{\"type\":\"rate_limit_error\"}"}}` is a rate limit, which Go reads as an error object without a type): `{"type":"invalid_request_error","type":"rate_limit_error"}` in a failure's `error` is a rate limit that cools the credential and is withheld from a WebSocket client, not a request fault forwarded as sent; the client still receives the bytes as they arrived when it receives the frame. On a WebSocket, a skipped frame whose failure reading would be an account failure, with the first or the last of a repeated key or, when a member the failure readings read repeats, with any other occurrence of it (`{"type":"response.future","type":"error","type":"response.future","status":429,...}` is withheld), is withheld and not classified, so the credential does not cool; Go's gjson reads only the first occurrence and forwards it. That includes a capacity message the failure reading composes from several members (`"code":"model","message":"at capacity"` beside a repeated `type`, a `param`, or a message taken from `response.error`). The response a decoded event names is its `response.id` as the pinned `Value` reads it, the last of a repeated `id`: a steering connection settles and accounts the response the pinned reader completes, where Go's gjson names the first. A readable `response.completed` names the response its `ResponseCompleted` reading carries, so `{"type":"response.completed","response":["r1",null,null,false]}` (the struct written as an array) settles `r1`, where Go's gjson finds no `response.id` and settles the latest response. Failure classification reads an event or wrapped status error written as a JSON array by the members the pinned client decodes it to: `["response.failed",null,null,{"id":"r1","error":{"type":"rate_limit_error",...}},null,...]` is a rate limit that cools the credential and is withheld from a WebSocket client, where Go's gjson reads no `type` and forwards it. A skipped frame repeats a member only when its path repeats (the same key in one object or in a repeated ancestor): `error.type` beside `response.error.type` is read by the first and last readings alone. A frame that is the WebSocket reader's wrapped status `error` is decided by the pinned mapping (`responses_websocket.rs:712-764`), on an upstream socket: an HTTP error status fails the turn by that status; `previous_response_not_found` or `websocket_connection_limit_reached` fails it whatever the status; a success status (2xx) or a status outside 100-999 makes it a notice that passes as sent, ends nothing and cools nothing (unless it would read as an account failure, when it is withheld), where Go fails the turn on any positive status and cools the credential. A decoded `error` that carries a status but is not a wrapped frame is a notice, whatever Go's integer reading makes of that status, because the pinned `error` branch reads no status: the status does not read as the wrapped struct's `u16` (`"429"`, `" 429"`, `"+429"`, `429.0`, `4.29e2`, a private number or raw value), or the struct refuses the frame (`status` beside `status_code`, a repeated `status`, a private raw value as `error.code`). Go fails the turn on such a frame with the status it coerces and cools the credential; the native WebSocket route reads on to the real completion. A notice still fails on a terminal provider code the pinned `Value` reads (`budget_reached`, `model_not_found` and the others of `error.rs:79-127`), resolved or not, and keeps Go's status for the scheduler when that is an error status; only a decoded `error` with no status at all keeps the status-less failure reading. A failure slot a pinned struct refuses is still read by position for account safety, never for classification: a `response.failed` whose `response.error` array the `Error` struct refuses (`["rate_limit_error","rate_limit_exceeded","..."]`, too short) keeps the pinned generic failure, a 502, and is withheld from a WebSocket client when its elements, named as `Error` names them, read as an account failure; a wrapped array neither pinned struct accepts (`["error",400,{"type":"rate_limit_error","code":{"$serde_json::private::RawValue":"\"budget_reached\""},...}]`) stays skipped, and is withheld when its elements, named as `WrappedWebsocketErrorEvent` names them, read as one. Go forwards both as sent. The translated route keeps Go's reading.
- Codex upstream-socket loss during a turn's failover: Go's Responses WebSocket handler closes the client when the executor reports an upstream disconnect, outside a duplex stream, whatever the turn is doing (`openai_responses_websocket.go:316-330`). In cliproxy-rs, a loss reported before the turn's request was served is the loss of a socket the turn's own attempt already failed on (an initial account failure, say): that loss does not close the connection, and the turn fails over to another credential or delivers that failure itself. Each socket's loss is its own, as Go keeps the disconnect error per connection (`resetUpstreamDisconnectError`), but where Go notifies only once per session, the replacement socket's later loss still closes the client, and a failure on it renders its own error, never the earlier socket's. A loss replaces only the failure of the attempt that acquired that socket: an attempt that fails before it serves on a socket (over HTTP, on another provider, or refused while it prepares its request) renders its own failure, and a socket already lost reports nothing once a new attempt starts. The loss of a retained socket the current attempt did not acquire does not end that attempt's turn; Go's notifier closes the client, and cancels such a turn, on any disconnect outside a duplex stream. A later `previous_response_id` continuation for that lost socket still gets the replay close (1012) and is never sent on a new socket. After the request was served, a loss closes the client as in Go.
- Codex response steering, a first response without `response.created`: Go's duplex reads a connection's later client frames only after the first `response.created` (`codex_websockets_duplex.go:391`, 601-605). When upstream ends the first response with its terminal event alone, Go delivers that event, but a later `response.create` gets no answer and the first response's record is published only when the connection ends. cliproxy-rs settles the bootstrap create with that terminal event, publishes its record then with the terminal's usage, and runs the next create on the same socket with the bootstrap's settings. It invents no `response.created` (docs/codex/CONTRACT.md "Responses and failures").
- Codex and xAI WebSockets: writing one frame upstream is bounded to 10 seconds, or to the frame's size at 128 KiB per second (rounded up) when that is longer. A write past the bound fails like any other write: if the upstream already closed the socket with 1009 (message too big), the request gets the same 413 as a failed write; otherwise the socket is dropped and the request is retried once on a new socket, or answered with a replay request on a continuation. On Codex the retry happens only when the frame provably never left (the next entry); a timed-out or failed write that may have sent part of it is never retried. On a steering (duplex) stream, a failed or timed-out write after the stream started ends the stream with that error. A client's `response.interrupt` written to the socket of the turn in progress has the same bound; when that write fails the socket is dropped, and the client gets the write error as a 400 error event (Go returns the error and leaves the socket to its reader). Go sets no write deadline, so a half-open socket held the request until the 300-second read deadline.
- Codex WebSocket requests the upstream may already have read (N1 [#111](https://github.com/zakstak/cliproxy-rs/issues/111), docs/codex/CONTRACT.md "Socket and account ownership"): once a `response.create` was written to an upstream socket, a loss before anything reached the client (a close with any code, a dropped connection, an idle timeout) and a write that failed after it may have sent part of the frame are request-scoped failures: the turn neither fails over to another credential nor cools this one, and the client connection closes as on any lost socket. This holds under `stream-bootstrap-buffering` after `response.created` was held. Go v8.0.35 has no outcome-unknown rule: the loss is a statusless executor error (ported here as a transport fault), which may fail over to another credential and run the same request twice on two accounts. Go v8.0.67 does not replay either, but answers `upstream_websocket_lost` and keeps the downstream socket open (`sdk/cliproxy/executor/websocket.go`); cliproxy-rs keeps its contract's close. A send is retried once on a fresh socket only when the frame provably never left: the socket's loss was recorded before the write, the write failed or timed out before the frame was handed to tungstenite, or tungstenite refused it before queueing (closed, closing, or a full write buffer). The same rule holds over HTTP for a Codex credential without `websockets` and on the native HTTP route: only a connection that could not be made, or a request whose deadline passed before it left, fails over. A lost answer, or a broken body after a success status, is request-scoped (Go v8.0.35 and the earlier port fail those over). Go retries every non-413 write failure (`shouldRetryCodexWebsocketSend`). An explicit upstream rejection, such as an overload or a wrapped status error, keeps its failover.
- Responses WebSocket client authority (N1 [#111](https://github.com/zakstak/cliproxy-rs/issues/111)): the client key is checked at the upgrade and again before every frame that would reach an upstream. That covers each turn as it is admitted and right before a Codex `response.create` is written, each later frame of a `codex.response-steering` connection as it is admitted and right before it is written, and each `response.interrupt`. The check re-runs the upgrade's authentication on the upgrade's headers and query against the current config. It runs at admission, and again at the write: after the upstream socket's lock, readiness and earlier flushes, or, for a turn over HTTP, before each attempt dials and again once its connection is up, before any HTTP byte. A turn over HTTP under a client authority therefore dials a connection of its own for each attempt, unpooled (no `chatgpt-keep-alive` reuse, no shared HTTP/2 connection), with the same TLS client, ALPN and proxy; Go shares pooled connections. A refused frame reaches no upstream, and the client gets a 401 `error` event with the authentication message (`Invalid API key`, `Missing API key`) or `client credential changed during the websocket stream; reconnect`, never a key. At admission the connection stays open; a refusal at the write ends the turn or steering stream with that event. Go v8.0.35 authenticates only the upgrade. Go v8.0.67 reauthorizes ordinary turns and duplex creates (`b9bb031d`), but on an ordinary turn it adopts whichever accepted key the request presents; cliproxy-rs never moves a connection to another principal, on any path, as Go does only for duplex turns (`3e7a21e2`). Go does not check interrupts or `response.steer`; cliproxy-rs checks every client frame it would send.
- Codex stream bootstrap buffering holds `response.metadata` (N1 [#111](https://github.com/zakstak/cliproxy-rs/issues/111)) as well as `codex.response.metadata`. An explicit `server_is_overloaded` after it still fails over, a failed attempt's metadata never reaches the client, and a serving attempt's metadata is released unchanged and in order. Go v8.0.35 releases the buffer on `response.metadata`, so the overload after it reached the client; Go v8.0.67 holds it (`9e79552f`, from an upstream capture in Go issue #6856). The pinned first-party reader takes no response content from that event (`sse/responses.rs:213-290`).
- First-party Codex terminal request rejections (FP2 [#116](https://github.com/zakstak/cliproxy-rs/issues/116), [codex/FP2-TERMINAL-ERRORS.md](codex/FP2-TERMINAL-ERRORS.md)), Codex credentials only. First-party Codex at research main `5c3ff1dabf64` never retries `inference_hook_denied` (no status or 403), `content_policy_violation` (no status or 400), `invalid_access_program` and `unsupported_access_program` (no status), `access_program_not_enabled` (no status, or a 403), or a 403 workspace denial (`invalid_workspace_selected`, `codex_workspace_access_denied`), whose code a 403 names in `/detail/code`, `/error/code` or the base64 `x-error-json` header. Go v8.0.35 knows none of these: a 403 one fails over to another account and cools the first, and an in-stream one without a recognised `error.type` gets Go's default 502 and also fails over when nothing was delivered yet. cliproxy-rs reads each as a terminal request rejection: the request stops on the selected account, no account cools, no token is refreshed, and one failed usage record is kept. An in-stream event, or a WebSocket `error` frame the first-party wrapped mapping leaves unmapped (no status, a 2xx or out-of-range status, or a status its struct cannot read), is read with no status, as research main reads it; such a frame with `context_length_exceeded` is therefore a context-window failure where the pinned reader read on. A wrapped status frame and an upgrade refusal are read with their HTTP status. A terminal rejection decides before Go's usage-limit and model-capacity readings of its message and keeps its status, any of these codes on a status other than its terminal one or 400 is no request fault, whatever Go's `invalid_request_error` type rule says, since first-party Codex retries it there, and on 400 it is terminal. A context code with 400, or in-stream, is never turned into a 429 or a bootstrap overload by its message. A frame Go reads as an account failure stays withheld from a native WebSocket client even when FP2 classifies it with another status. Bodies are read with the last of a repeated key. `context_length_exceeded` with any HTTP status other than 400 is no request fault and is not rewritten to `context_too_large`: a 503 keeps its transient meaning and fails over and cools as Go's 503 does. The native HTTP route still delivers the provider's status and body; a native WebSocket client never receives a 403 one, as a frame or as an exposed error (#6), and gets a silent close. The executor carries the reading on `ExecError::sourced`; the server's Go request-fault rules are unchanged for Claude, xAI and Meta, which never set it.
- Upstream connections: the Claude client for `api.anthropic.com` keeps every idle connection for 90 seconds. Go's transport for it keeps at most 2 idle connections per host (net/http's default) with no time limit, so after a burst of concurrent requests Go dials again and cliproxy-rs does not.

Go's deadline also covers the body.
- Quota cooldowns (`routing.cooldown.max-trusted-cooldown`, a bug fix, on by default): when an upstream answers 429 with a reset time (Codex `usage_limit_reached` with `resets_at`, Claude's `anthropic-ratelimit-unified-*-reset`, or `Retry-After` from any provider), Go rests the account until that time, even when it is days away, and never asks again. Providers often reset early, which leaves the account unused until the stated time or a restart, and with `save-cooldown-status` a restart restores the same wait. cliproxy-rs rests the account for at most one hour at first, then lets the next ordinary request through as a check (no timer or background request). Only that one request goes upstream: until it is answered (or for at most 30 seconds), other requests see the account as cooling, and retries never wait for such a window. Only the probe's own answer or cancellation ends the check: an answer or cancellation from a request picked before it, including an earlier probe whose 30 seconds ran out, neither frees the account nor opens the next window. A streamed answer counts as soon as its first event arrives, so other requests use the account while the stream runs. One exception: when one model of a pooled `openai-compatibility` model alias (several models under one alias name) has its own window (not the account's), requests for the alias that arrive together after that window ends can each probe that model, because the reservation is taken for the alias at pick time and the pool chooses its model later. Each window that ends in another 429 doubles the next, a success ends the escalation, and the rest never passes the stated reset except by Go's own additions: its 10-second minimum and the 1 to 30 seconds of random delay it adds to Claude's reset. A success from a request picked before the window opened (a stream that outlived the 429) leaves the window to its probe, even after the window ended; Go keeps a cooldown against such a success only while the cooldown runs, and clears it on any success dispatched after the 429. A concurrent 429 inside a window keeps the window, or shortens it when it states an earlier reset. The account's probe answers the account's window, not a model's own window: that model keeps its own probe time and gets its own probe. Under the account's bounded window, a model's own cooldown of any cause keeps its own deadline in that model's record, and the account's record holds the model until the account's probe, so an earlier account reset never brings the model back sooner; Go writes the later of the two deadlines into the model's record. The doubling count is separate from Go's `backoff_level` (which keeps its meaning) and is saved as an extra `quota.trust_windows` field on every quota record cliproxy-rs writes to `.cds` files, which Go ignores; records are saved only while their cooldown is running, so a restart after a window ended starts again at one hour. cliproxy-rs's own records restore as they were saved. `.cds` records written by Go or before this change get the first bound. A model's count is never lowered by a credential-wide window. The stated reset is kept: `.cds` records and error events report it as `quota.next_recover_at` (Go's meaning) and the probe time as `next_retry_after`, and the Management API's cooldown entries gain `recover_at`, so the dashboard shows "Limited until X · next check in Y"; such an entry stays listed, with `remaining_seconds` 0, after the window ends while the stated reset is ahead. The cost is one comparison per 429; a probe check on two keys per recorded result, per pick and per stream start; one scan of the cooldown entries when a stream start or a success ends an account's window; four bytes per cooldown entry and per request for the window generation; and per credential and model one real upstream request per window. `max-trusted-cooldown: 0` restores Go's behaviour. Set by a config reload, it applies to requests picked after the reload. A bounded window keeps its bound and ends with its probe, unless a 429 from such a request arrives inside it with a later stated reset, which then replaces the bound as in Go. Go starts with the key in `config.yaml` and ignores it; when Go's Management API rewrites the file, it moves the key into a comment, as it does with every key it does not know.

- Model cooldown keys and forced cooldowns ([#95](https://github.com/zakstak/cliproxy-rs/issues/95), from the selective Go v8.0.67 target). A cooldown is recorded and looked up under one key, the model this proxy sends upstream when it resolved the route to that model (Go `stateModelForExecution`, whose selection-to-upstream comparison now ignores case under `strings.ToLower`, `098af7d5`). Selection, probe holds and the registry projection use that key too; before, they used the selection model, so a configured model whose name differs from its alias only in case could be cooled under one client spelling and picked under another. Cooldowns saved or kept under a spelling that now resolves to another key move to it at startup, on a config publish and on a credential change, merging with the later deadline kept, together with a live probe reservation from either side, which its own request's accepted stream or result still releases. A request picked before a move records its result under the key its cooldown moved to: the scheduler keeps each move, for the credential revision it happened under, and a result follows the moves since its pick, whatever aliases are published later. A key moves only to the same name under `strings.ToLower`. An ordinary answer never brings a live forced deadline earlier, and a credential-wide failure keeps each model's own forced deadline. Records carry Go's `force_cooldown_until` and `force_cooldown_evaluated`; a record without the evaluated mark (an older one) is never treated as forced. Go's `cred_quota_force_cooldown_until` and `independent_force_cooldown_until` are not read: cliproxy-rs keeps one forced deadline per cooldown key. - CORS allowed request headers ([#104](https://github.com/zakstak/cliproxy-rs/issues/104)): every response, on every route, sends `Access-Control-Allow-Headers: Authorization, Content-Type, X-Api-Key, X-Goog-Api-Key, Anthropic-Version, Anthropic-Beta`, and an `OPTIONS` preflight answer appends each name from `Access-Control-Request-Headers` that the list lacks, once, in Go's canonical case. Go v8.0.35 sends `*`. Fetch never lets `*` cover `Authorization`, a CORS non-wildcard request-header name ([CORS-preflight fetch](https://fetch.spec.whatwg.org/#cors-preflight-fetch), steps 7.6 and 7.7), so a browser page that sends a client key as a bearer token fails its preflight against Go v8.0.35. Go v8.0.67 makes the same change (058b803b). Unlike Go v8.0.67, cliproxy-rs reads every `Access-Control-Request-Headers` line, not only the first, and drops a requested name that is not an HTTP token instead of echoing it, because one malformed name makes a browser reject the whole list. The origin (`*`), methods, exposed headers, the `204` preflight before routing and authentication, and the absence of `Access-Control-Allow-Credentials` are unchanged.
- RESP command bounds ([#102](https://github.com/zakstak/cliproxy-rs/issues/102)): on the main listener's Redis protocol, a command is refused with `ERR protocol error` when its count is negative, unparsable or above 1,024, when a count line, length line or simple or integer argument is longer than 64 KiB without its CRLF, or when a bulk length is below -1. It is refused with `ERR bulk string too large` when a bulk is longer than 64 MiB (previously `ERR protocol error`) or no longer fits the command's budget. The budget is 64 MiB plus 64 KiB per command. It counts every byte from the `*` to the last CRLF, plus the bytes that lossy UTF-8 decoding adds, and it starts again for each pipelined command. Go v8.0.35 has none of these bounds and reads any negative bulk length as an empty string. Go v8.0.67 (888f2382) uses the same 1,024-entry and 64 KiB line limits, but it caps each bulk, and the payload bytes of a whole command, at 64 KiB. cliproxy-rs keeps its existing 64 MiB bulk ceiling. Commands sent to the server carry only a management key, a channel name, a count or a `PING` message, and queue payloads flow only to the client, so no compatibility evidence supported a lower limit. A bulk buffer grows with the bytes that have arrived, not with the declared length. After a refused command, the server sends its reply, then a FIN, then reads and discards up to 1 MiB of the client's pending input for at most one second, so a reset cannot discard the reply. Go closes the connection at once.
- Incomplete requests on the main listener ([#103](https://github.com/zakstak/cliproxy-rs/issues/103)): an HTTP/1.1 request head must arrive within 10 seconds, counted from the moment the connection starts waiting for it, and an idle keep-alive connection is closed 10 seconds after its last response, because hyper runs one clock for both. A Redis protocol client must finish its commands within 10 seconds of reaching that protocol until `AUTH` succeeds; after that, reads have no deadline. Request capture reads no request body before client authentication (the client-key check of the API routes and of the realtime routes) admits the request. A request answered before that, such as a `401` for a missing key, a `410` for a removed provider or an unrouted `404`, is never read for the log: its request log or forced error log has an empty request body, and the connection closes after the answer instead of waiting for the rest of the body. The `413` that whole-body capture answers at `server.max-request-body-bytes` therefore comes after authentication: a request without a valid key gets `401`, and the `413` now carries the CORS headers that every other answer has. An admitted request is captured as before, and its body has no read deadline, so a slow authenticated upload or response stream is not cut. Go v8.0.35 bounds only a connection's first byte (10 s) and, before authentication, reads a body of at most 1 MiB, or any body with `request-log` on, so an unauthenticated client could hold a connection and its descriptor for as long as it sent nothing more. Go v8.0.67 (477605dc) adds the same 10 s `ReadHeaderTimeout` and Redis setup deadline and also captures bodies only after authentication. Unlike cliproxy-rs, it keeps idle keep-alive connections open without a deadline and logs an incomplete-capture marker for a body it never read. HTTP/2 connections, which only TLS with ALPN `h2` negotiates, have no request-head or idle deadline.
- SSE heartbeats ([#105](https://github.com/zakstak/cliproxy-rs/issues/105)): the `: keep-alive` comment that `requests.streaming.keepalive-seconds` adds to an idle stream is written only at an event boundary: after a blank line, with LF, CRLF or lone-CR line ends as `text/event-stream` allows (a CRLF read in two parts counts once), or before the first byte. A stream that forwards upstream reads as they arrive, such as the raw image streams of `/v1/images/generations` and `/v1/images/edits`, can stop inside a line or inside a multi-line event, where a comment would split or corrupt the event. A heartbeat that falls due there is skipped, and the next one is tried a period later. When such an image stream fails inside an event, its `error` event follows the line ends that close the cut-off event, so the error is never merged into it. Go v8.0.67 skips every CR when it counts line ends, so it treats an event that lone CRs end as unfinished. Go v8.0.35 writes the heartbeat wherever the stream stopped, and the error event straight after the cut-off bytes. Go v8.0.67 (91e0dee8) makes the same change for image streams only and also restarts the heartbeat period after each write. cliproxy-rs applies the boundary rule to every SSE stream it writes and keeps the fixed period. A stream whose writes all end on event boundaries gets the same heartbeats as before, and the forwarded bytes never change.

- Config writes: when the Management API changes one setting, the rest of `config.yaml` stays byte for byte as it was. Go re-encodes the whole file. Its v0 setters write it from typed values, which turns YAML 1.1 booleans such as `yes` and `on` into `true`; since v8.0.35 its v8 config API re-encodes the parsed document instead, which keeps such values as written but rewrites every non-empty flow collection in the file as a block and unquotes double-quoted keys; cliproxy-rs writes the values it changes that way and leaves untouched flow collections such as `api-keys: [a, b]` as they are. Go v8.0.35 writes the plaintext, and its background reload after the save then hashes it and rewrites the file, so the plaintext stays on disk until that reload runs. - Config writes, body upload: a v8 config write (`PUT`, `PATCH` or `POST` under `/v8/management/config`) checks the stored file, its `If-Match` precondition and the stored config's parse under the config lock, as Go does before it reads the body, then releases the lock while the body arrives and repeats those checks under the lock before it writes. Go holds its lock through the upload, so a slow client delays every other config save; in cliproxy-rs another save can land while a body is uploading, and the write then answers `412` (with `If-Match`) or applies to the newer file.
- Config YAML, tags and anchors: the config load reads tagged scalars as yaml.v3 does: a `!!binary` scalar (and its aliases) is its base64-decoded text, a scalar with an unknown local tag (`!keep x`) is its text, a plain scalar with the non-specific `!` tag is null when it spells null and otherwise its own text, and the literal short tags `!<!!binary>`, `!<!!null>` and `!<!!str>` act as the standard ones. It refuses to load, where Go loads, a file with: a `!!binary` value whose bytes are not UTF-8 text (a setting holds a Rust string; Go stores the bytes); an explicitly tagged mapping key, whatever the tag (`!!str <<:` is an ordinary key in Go, not a merge), an aliased mapping key, or a mapping or sequence used as a key (Go rejects those too); a quoted `<<` key (`'<<':`, `"<<":`, an escape such as `"\x3c<":` or a block scalar), which Go reads as an ordinary key and cliproxy-rs would merge; a merge source that an explicit key or an earlier merge source shadows but is not a mapping or a list of mappings, such as `server: {port: 1}` beside `<<: {server: {<<: 5}}` or a `<<: *s` there naming a sequence (refused with Go's `yaml: map merge requires map or sequence of maps as the value`; Go never decodes a shadowed merge source and loads `server.port` 1); a non-specific `!` tag on a plain value that does not start with a letter or is a boolean word (`! 8317`, `! ---`, `! yes`), since telling those apart would need a YAML resolver Go and cliproxy-rs do not share, or another literal short tag on a scalar such as `!<!!int> 1` (on a mapping or sequence any tag is read by its kind, as in Go); a `%00` anywhere in the source of a tagged node or of a document's directives (the YAML library cliproxy-rs uses cuts a tag at the NUL, Go keeps it); and an anchor name defined twice (the YAML library binds an alias of a redefined anchor to a different node than Go does). Preparing a file for a remote store reports the same refusals, the management config routes, which read the file the same way, answer `500 invalid_config` while the file on disk is one of them (Go can serve such a file's YAML and JSON views and accept writes to it), and a body sent to `PUT /v0/management/config.yaml` with a quoted `<<` key is refused with `400 invalid_yaml`. Go accepts it and never merges it: a legacy-layout body is saved as sent (apart from its comment indentation) and loads the quoted key as an ordinary key (`"<<": {port: 1}` loads with port 0); in a v8 or mixed-layout body, Go's layout normalization comments the key out as an unrecognized section (`server: {"<<": {port: 1}}` is saved as `server: {}` and a `# "server.<<": {port: 1}` comment).
- Config YAML, tagged numbers: a scalar tagged `!!int` or `!!float` whose text the YAML library cliproxy-rs uses does not read as that type, such as `!!int 007`, `!!int 1_000`, `!!int 0X1F` or `!!float 1_0.5`, refuses the file with that library's `invalid value` error. Go loads it: yaml.v3 reads it into a string setting as its text and resolves it into a number setting.
- Config YAML, integers beyond 64 bits: a plain integer outside int64 and uint64 that fits 128 bits reads as yaml.v3 reads it (a decimal one as a float, `0x…`, `0o…` and `0b…` as text, a string setting as its text). Still refused where Go loads the file or body: such an integer with a local tag (`!keep 18446744073709551616`); two such mapping keys that round to the same float (`duplicate entry`); one used as a key of a config map (`config keys must be strings`; Go uses its text); and a negative one in an int setting (`-100000000000000000000`, which Go stores as the minimum int64). Where a save writes a section out again (migrating a legacy-layout file to the v8 layout, or archiving an unknown key as a `# key:` comment), such an integer is written as its float (`1.8446744073709552e19`) or quoted (`'0x1FFFFFFFFFFFFFFFFF'`), so a string setting or a plugin reading the saved file gets that text, where Go keeps the integer's text.
- Config YAML, numbers with underscores or a leading zero: a plain `1_000`, `0x1_F`, `1_0.5`, `007`, `08` or `0b-1` reads as yaml.v3 resolves it (1000, 31, 10.5, 7, 8.0, -1), and a string setting keeps its text, as in Go. Where a save writes a section out again (migrating a legacy-layout file to the v8 layout, archiving an unknown key as a `# key:` comment, or a v8 write that replaces a whole list), such a number in a value that is not a string setting is written as its value (`007` as `7`, `08` as `8.0`, `1_0.5` as `10.5`), where Go keeps the node's text; the value read back is the same. Such a mapping key stays text and is written quoted (`"1_000":`). Upper-case prefixes read as in Go too (`0X1F`, `0O17`, `0B10`: 31, 15, 2), and a `+` integer past int64 reads as Go reads it, a decimal one as a float (`+9223372036854775808`) and any other as text (`+0x8000000000000000`).
- Config YAML, plain timestamps: a plain `2001-12-14`, `2001-12-14 21:59:43.10` or `2001-12-14T21:59:43.10-05:00` in a value without a typed setting, such as a payload rule param or match value, reads as yaml.v3's `time.Time`, as in Go: payload rules, raw ones included, send it as its RFC 3339 text (`"2001-12-14T21:59:43.1-05:00"`), and the JSON views show that text, the v8 view for a string setting too, which loads its own text. Where a save writes such a value out again (migrating a legacy-layout file, or archiving an unknown key as a `# key:` comment), it is written plain as that RFC 3339 text (`2001-12-14T00:00:00Z`), where Go keeps the node's text (`2001-12-14`); the value read back is the same. A string, key or value, that reads as a timestamp is written quoted, as Go writes it. A file holding a plain timestamp value with a zone offset of 24 hours or more (`2001-12-14T21:59:43+24:00`), string settings included, is refused, and so is `cliproxy discover` reading it: Go loads it but cannot marshal that time as JSON, so its payload rules skip the param and its JSON views fail, and Go's discovery reads only its own settings. Such a key is not refused. Still read differently: a scalar tagged `!!timestamp` is its text (Go: a `time.Time`), so a `*-raw` payload rule holding one is dropped as invalid JSON where Go applies it; and an anchored timestamp key used as a value through an alias (`&k 2001-12-14: a`, `x: *k`) is text, where Go has a `time.Time`, as with `&k 007:`.
- Config YAML, number and timestamp keys in untyped values: a plain key that yaml.v3 resolves to a number or a timestamp (`1:`, `007:`, `2001-12-14:`) in a mapping nested inside a value without a typed setting, such as an object-valued payload rule param or a match condition, makes yaml.v3 build a `map[interface{}]interface{}`, which Go's JSON encoding refuses: Go drops that param, a `match` condition holding it never matches and a `not-match` one never excludes. Go's v8 view decodes the whole config into `any`, so such a key anywhere, even in a typed map such as `oauth.excluded-models: {007: [a]}` or `{2001-12-14: [a]}`, makes `GET /v8/management/config` answer an empty `200`. cliproxy-rs sends or shows the key: `1:` is read as the number 1 and shown as `{"1": …}`, and `007:`, `1_000:` or `2001-12-14:` stays text (`{"007": …}`).
- Config YAML, alias copies: a file whose aliases copy more than 1,048,576 scalars that the load reads as yaml.v3 does instead of as its YAML library does (`!!binary` and other tagged values, and numbers or booleans such as `0x1F` in a string setting) is refused with `config YAML aliases expand too far`. Scalars written in the file do not count, and neither do copies of an anchored list into a position outside any anchored list or mapping. Alias copies of numbers or booleans that land inside an anchored list or mapping do count, even when no alias puts them in a string setting. Go refuses a file with many aliases compared with its size as excessive aliasing (`yaml: document contains excessive aliasing`), so it refuses `x: &x [0, …]` with 1,025 numbers and `y: &y [*x, …]` with 1,024 aliases of it (7 KB) too, but loads the same lines beside about 600,000 padding numbers (1.8 MB), which cliproxy-rs refuses. It also loads a large file whose aliases make that many copies outside anchors, such as 600,000 padding numbers beside 1,050 `oauth.excluded-models` channels that each alias a 1,000-number list. Aliases may also visit at most 4,194,304 anchor entries in all, kept as copies or not (a number an alias puts outside any string setting is dropped), and a file past that is refused the same way. Go refuses those files too, as excessive aliasing, whatever key the aliases sit under, including keys the config does not read: 2,048 aliases of a 2,049-number list under an unknown root key fail in Go in milliseconds. In the Management API, a YAML upload over either limit is refused with `400` and `config YAML aliases expand too far`, and while the file on disk is over one the v8 management config routes answer `500 invalid_config`, where Go serves any file it loads.
- LAN discovery without interface filters on the command line (`cliproxy discover`, `-discover`): cliproxy-rs reads `discovery.interfaces` from `config.yaml` with the config decoder, so a file it refuses makes the command exit 1 with the refusal instead of scanning. That covers invalid `!!binary` data anywhere in the file, a merge of something other than a mapping (`<<: 5`, or an alias of a sequence, which Go's decoder also fails) and the restrictions under "Config YAML, tags and anchors". Go decodes only the discovery section and scans: with no filters when that section fails to decode (`include: [!!binary '!!!']`), with the file's filters when the problem is elsewhere (invalid base64 under `proxy-url`). A missing file or a YAML syntax error scans with no filters in both.
- Config YAML, saved `!!binary` values: management saves keep the text of each `!!binary` scalar they do not change. Where a save writes a setting out again, as a v8 write does when it migrates a legacy-layout file to the v8 layout, the value is saved as its decoded text without the tag; Go moves the tagged node. The saved value is the same. A `GET /v8/management/config.yaml` of a legacy-layout file shows such a value in the migrated sections as its decoded text, where Go shows the tagged node.
- Config YAML, saved numbers in string settings: a management write that re-emits a section saves a string setting written as a plain number or boolean quoted (`'1.50'`, `'0x1F'`, `'True'`, `'007'`, `"1_000"`). Sections are re-emitted when a legacy provider-key section is migrated to `api-keys`, when the comment-preserving migration cannot move a legacy layout, and when the file cannot be edited in place, in which case a v8-layout file is written out again whole and quoted too. The loaded value is Go's, but the v8 JSON view then answers the string (`"1.50"`, `"1_000"`) where Go, which keeps the plain node, answers the number or boolean (1.5, 1000). A `GET /v8/management/config.yaml` of a legacy-layout file likewise shows those settings in the migrated sections quoted, where Go shows them plain. A v8 JSON write (`PUT` or `PATCH`) that sets a string setting to a number whose text the save would not write back as it is (`1.50`, `1e3`) also saves it quoted, as its text, which loads as Go's value, and the v8 JSON view then answers the string (`"1.50"`) where Go answers the number (1.5); a number it writes back as it is (`5`) is saved plain, as in Go.
- Config YAML, `client.codex.web-search-result-cache`: Go's custom unmarshal and `Validate` refuse values that cliproxy-rs, which checks the section only against its Go field types, accepts: a `ttl` of `0x1F`, `abc`, `yes`, `"true"`, `'1.50'`, `1e3` or `-5` (Go takes only a plain string or integer that parses as a non-negative duration or seconds); an `enabled` of `yes` or `on`, read as true (Go takes only a YAML boolean); a `limit` of `1.5`, read as 1, or `-1` (Go takes only a non-negative YAML integer); and an unknown key inside the section, which Go fails on load and cliproxy-rs loads (its strict writes and the v8 migration treat it as Go does). Where Go fails the load or the management write, cliproxy-rs loads or saves. The setting has no effect in cliproxy-rs yet: the web search result cache is not ported.
- v8 config writes, decode error text: where Go's `PUT`/`PATCH /v8/management/config...` refusal is yaml.v3's typed-decode error (``parse config payload: yaml: unmarshal errors:\n  line 11: cannot unmarshal !!str `bad` into int``, the strict decode's `field unknown not found in type registry.CatalogSources`, or a custom decoder's wrapper around one, such as `parse plugin enabled: yaml: ...`), cliproxy-rs names the setting instead (`parse config payload: config.server.port has an invalid type`, `unknown setting config.models.unknown`), with the same status and error code. Go's line numbers count lines of its own re-marshaled candidate, and its type names are Go's. Other refusal messages are Go's text, apart from the refusals listed elsewhere in this file.
- `multimedia.disable-image-generation` given as a number (`disable-image-generation: 1`): cliproxy-rs refuses it (`config.multimedia.disable-image-generation has an invalid type`). Go parses the number's source text like a string, so `0` and `1` select off and on, and `0x1` or `1.0` fail with `invalid disable-image-generation value "0x1" (allowed: true, false, chat, passthrough)`; the parsed value no longer tells those apart. Booleans, null and strings are read as Go reads them, with its error text.
- Management key hashing, rewritten file: when a plaintext `secret-key` cannot be replaced in place (it is shared through a YAML anchor or merge, or its node cannot be edited), Go rewrites the whole alias-expanded document and keeps each scalar's text. cliproxy-rs writes the expanded tree from parsed values without tags, so it refuses the rewrite when the document has any explicit tag (`!!binary`, `!!str`, a custom tag, the secret's own included), any mapping key that is not a string (`0x1F:` would become `31:`), any plain timestamp value (`2001-12-14`, even one already written as `2001-12-14T00:00:00Z`), or any other scalar whose text would change (an unquoted `0x1F` would become `31`, `0.50` would become `0.5`). So a file whose secret is shared through an anchor or merge and which also holds a plain timestamp does not get the plaintext secret hashed, where Go hashes it. Preparing a file for a remote store then fails with `rewriting the config file would change the text of another setting`, where Go uploads the re-encoded file (for example a merged secret beside `server.host: !!binary ...` or a hex key) or refuses because the plaintext is still present; an ordinary startup keeps the hash in memory and leaves the file as it is, as it does on a read-only mount.
- Management key hashing, tag directives: preparing a config file for a remote store refuses with `the management key's YAML tag cannot be resolved for upload` when the `secret-key` value is tagged and the file has a `%TAG` directive, or the tag uses a named handle. Go resolves the handle (so `%TAG !e! tag:yaml.org,2002:` makes `!e!binary` a base64 secret, and `%TAG !! tag:example.com,2000:` makes `!!binary` an ordinary string) and prepares the file. The same refusal applies when the `secret-key` value is reached through an alias, a merge or an aliased section and the file has any tag that is or could be the binary tag: Go follows the alias to its tagged target and decodes it, and cliproxy-rs does not resolve that. Shorthand and verbatim tags with `%XX` escapes, and tags that resolve to the short spelling `!!binary` (`!<!!binary>`, `!%21binary`), are resolved as Go does.
- Management key hashing, Unicode line separators: preparing a config file for a remote store refuses any file that contains U+0085 (NEL), U+2028 or U+2029, with `the config file contains a Unicode line separator yaml-edit cannot read`. yaml.v3 ends a line at those characters, and the syntax tree cliproxy-rs edits through does not, so a comment ending in one would hide the next line from the secret's tag check. Go prepares such a file, including one where the character is only string content.
- Watcher: when a config change moves `auth-dir`, cliproxy-rs starts watching the new directory. Go keeps watching the old one until it restarts.
- Watcher, where file change notifications cannot be set up (inotify instance or watch limits): cliproxy-rs logs one warning and checks the config file and auth files every 2 seconds instead. Go stops at start: with `cliproxy: failed to create watcher` when the inotify instance cannot be created, and with `cliproxy: failed to start watcher` when the config file or auth directory cannot be added. As in Go, changes made by another machine on a network or FUSE file system can go unreported until the next local change: on NFS, 9p (such as WSL2's /mnt/c) and sshfs they are not reported, and on SMB/CIFS shares they may not be, depending on the server.
- Watcher, symlinks: cliproxy-rs also watches the folders that hold symlinks on the way to the config file, the auth folder and symlinked auth files, so a Kubernetes Secret update (the `..data` swap) or an `ln -sfn` to a new release folder is reloaded. Go's fsnotify watches only the config file and the auth folder and misses those.
- Auth files that cannot be read ([#89](https://github.com/zakstak/cliproxy-rs/issues/89)): cliproxy-rs follows Go v8.0.67 (`5fe203d5`, `57a12996`) instead of v8.0.35. An auth file whose read fails for any reason except "not found" (permission denied, an I/O error, a symlink loop) keeps the credential last loaded from it. So does every file in an auth folder that exists but cannot be listed. When a listing fails partway, only the files it never reached are kept; a file it reached is settled by what was found (a file read and refused, gone or not a regular file still loses its credential). The credential keeps its revision, cooldowns, 401 block and saved-document binding until the file can be read again or is deleted. Go v8.0.35 drops such credentials on its next full scan. These cases are handled as before: a file that is gone, a dangling symlink, a symlink to something that is not a regular file, empty or partial JSON (kept, Go `7484a521`), valid JSON without a credential, a removed provider's file and retired metadata. The watcher records an unreadable file with the hash last read from it. Losing access therefore triggers no reload, no `auth file changed` line and no remote-store push, while deleting the file is seen as a removal. A write whose read fails at any stage stays pending: the watcher's own read or folder listing, the reload's scan, or the freshness check when the scan is published. The watcher checks pending files on the next file event, or every 2 seconds while idle, and reloads as soon as they can be read. A re-login or revocation hidden behind one transient error is therefore applied with no further write or file event. A lasting denial does not reload repeatedly. A Management API save, a login or a config edit also rescans the folder, and the same rule applies there. An upload fallback whose file cannot be read stays registered. A kept credential is the store's current one when the scan is published, so a token refresh committed after the scan is not undone.
- Token refresh: the refresh loop sleeps until the next token is due and looks again at least every 10 minutes of awake time while any credential can come due. Go looks every 30 seconds. After a computer wakes from sleep or the clock jumps forward, a token that expired in the meantime is refreshed by the first request that gets a 401 (one extra round trip; the other credentials are refreshed about a second later) or within 10 minutes.
- Refused tokens after an upstream 401: when the refresh an upstream 401 starts fails with `invalid_grant` while the access token the upstream refused is still the credential's, the credential is no longer selected or refreshed until its tokens change (a new sign-in, an upload or an edited file), as in Go. The credentials list shows it as `error`, unavailable, with the status message `unauthorized (refresh token invalid)` and no retry time. The block lives in memory: a restart tries the credential again, where Go keeps the state until its tokens change. A disabled credential, or one whose access token is empty, is never blocked this way. Go compares only the access token; cliproxy-rs also leaves the credential unblocked when any of its other token fields (refresh token, ID token, API key, Sign in with ChatGPT tokens) changed between the 401 and the refused refresh, so a rotation in that window is never mistaken for a refusal. The check and the record are one step, so a rejection never lands on tokens that replaced the refused ones, nor on a credential removed, or removed and imported again, while the refresh ran; removing a credential forgets its rejection, so importing the same tokens again tries them again. A 401 that arrives while another 401's refresh is running waits for it and, when that refresh was refused, sends nothing. A blocked credential is skipped by the Antigravity credits fallback too.
- Disabled credentials and refresh: a disabled credential is not refreshed; when its refresh comes due, one line is logged per revision (`credential refresh for claude (a.json) is due but the credential is disabled; it is refreshed once it is enabled`). Go keeps refreshing a disabled credential unless its last error was `invalid_grant`, backing off 5 minutes after each failure.
- Token refresh logging: every failed refresh, whether the refresh loop or an upstream 401 started it, logs one warning with the provider, the credential ID, the status, the error and when the next attempt is, for example `credential refresh failed for claude (claude-a.json) after an upstream 401: status 400: Claude OAuth acquisition failed: invalid_grant; next attempt in 60s`. A built-in executor's error text is sanitized as client-facing upstream errors are. Go logs those refresh outcomes at Debug (`refreshAuthForRequestAtEpoch`, `tryRefreshAfterUnauthorized`), with the whole error; for Claude it also warns once per token endpoint attempt, with the whole response body. cliproxy-rs keeps nothing of a Claude token endpoint's error body except a known error code (the eight RFC 6749 codes, such as `invalid_grant` and `server_error`, and Anthropic's seven error types, such as `authentication_error`), since that endpoint is sent the refresh token; the invalid-grant backoff reads it as Go's does. One refresh job per credential runs at a time, as in Go. A job that has run 5 minutes since it got a worker (`oauth.auth-auto-refresh-workers`; the wait for the credential's preparation lock included) logs that it is still running and gives its worker to the next job, so one stuck refresh cannot hold up the others. It runs on and records its own result (tokens its exchange rotated are still saved) and wakes the refresh loop when it ends, and no other refresh of that credential starts until then, which a due refresh logs once. A refresh job that panics fails like any refresh and backs off. A refresh loop that panics logs an error and starts again. In Go each refresh worker waits for its own job (`auto_refresh_loop.go`), so a stuck job holds a Go worker indefinitely.
- Model catalogs: outside Home mode, the default source of the Codex client catalog (no `models.codex-catalog` and no `--local-model`) is first read when a Codex credential exists, a Codex client asks for `/v1/models?client_version=...`, or a Codex client sends a Responses request with `client.codex.optimize-multi-agent-v2` on; that of the Devin catalog when a Devin credential exists; and the Antigravity client version (the Antigravity Hub updater manifest every Antigravity user agent carries) when an Antigravity credential exists. Go starts all three at launch and refreshes them every three hours whether or not they are used. An explicit source, `--local-model` and the models.json catalog start at launch, a config reload that changes a catalog's source switches it at once, and in Home mode the Codex catalog and the Antigravity version start at launch, all as in Go. `--local-model` does not keep the Antigravity client version local, as in Go. Until the first manifest download, Antigravity requests carry the built-in fallback version, as Go's do until its first download finishes. Until the first Codex catalog read, Codex client catalog answers and the `spawn_agent` model lists use the catalog built into the binary; after it, they match Go. Until the first Devin catalog read, the Management API's model definitions for the `devin` channel list the Devin catalog built into the binary, so outside Home mode they stay that catalog until a Devin credential exists; Go lists the downloaded one.
- Model catalog reads: a remote catalog source (an http(s) `models.catalog` or `models.codex-catalog`, or the router-for-me default) is read with a 30-second bound on the request, its redirects included, and a separate bound on the body of at most the time that was left. Go reads it through `http.DefaultClient`, which has no timeout, so a stalled source holds that catalog's updater until its source changes or the process stops. Both use the environment proxy, not `proxy-url`. The URL and every redirect hop are built as Go's `net/url` builds them: the source is parsed as `url.Parse` parses it, each redirect `Location` is resolved with `URL.Parse`, and each request is sent with `URL.RequestURI`, so dot segments stay as written and the path is escaped as Go escapes it (`/my catalogs/../m.json` is requested as `/my%20catalogs/../m.json`, `/a%2Fb/x|y.json` as `/a/b/x%7Cy.json`). A source Go fails to parse or that has no host, and a redirect whose `Location` Go fails to parse or whose resolved URL has no host, fail the read in both. cliproxy-rs refuses, where Go reads the source: a non-ASCII host (`https://bücher.example/...`) or a host with a percent escape, which includes an IPv6 zone (`http://[fe80::1%25en0]:8080/...`), in the source or in a redirect; a host the WHATWG URL parser that routes each request rejects, such as one whose last label is a number but which is not an IPv4 address (`http://catalog.internal.1/m.json`) or one with an `xn--` label that is not valid IDNA (`http://xn--a.example/m.json`), which Go resolves through DNS, in the source or in a redirect; a port Go writes in the `Host` header that the HTTP library would leave out: the scheme's default port written out (`http://h:80/m.json`, `http://h:080/...`, `https://h:443/...`) in the source or in a redirect, and an empty port (`http://h:/m.json`) in a redirect (Go drops an empty port in the source, and so does cliproxy-rs); a request target the HTTP library does not carry as written, such as a query holding a space, `"`, `<` or `>`, or a URL longer than 65,534 bytes; and a redirect whose `Location` is not valid UTF-8, which is not followed: the 3xx answer fails the read, where Go follows it. Each of these counts as a failed read and keeps the last valid catalog.
- v0 setters over a refused file: a deprecated `/v0/management/...` setter edits `config.yaml` as it is on disk and validates the result. When the file holds a setting a reload refused, such as a relative `models.catalog`, the write answers `422 invalid_config` with that setting's error and the file stays as it is; the running config keeps the last valid values. Go marshals its valid in-memory config over the file and saves, which replaces the refused value with the running one.
- v0 `config.yaml` uploads with several errors: the upload checks the model catalog sources before it decodes the setting types, so a document that also holds a mistyped setting or a nonnumeric legacy weight can name the invalid source where Go names its YAML decode error first. Both answer `400 invalid_yaml`; for example `models: {catalog: [bad], devin-catalog: relative.json}` names the `models.devin-catalog` source here, where Go reports `yaml: unmarshal errors:` with `cannot unmarshal !!seq into string`.
- Remote model catalogs: a refreshed `models.json` is refused whole, and the catalog in use is kept, where Go would decode it differently from the members cliproxy-rs keeps. That happens when a section (`claude`, `gemini` and the others), a model field, a `thinking` field, `config.override_header` or a `native_capabilities` field is named in another case, or appears more than once in the same object, case-folded. It also happens when an integer field holds anything but an integer literal. Go matches those names case-insensitively and decodes repeated members one after another into the same field, so it serves `{"thinking":{"Min":1}}` with `min` 1 and `"inputTokenLimit":1,"InputTokenLimit":2,"inputTokenLimit":3` as 3. It merges a repeated `thinking` object and serves a lone `GEMINI` section as `gemini`. Go refuses fractions such as `0.0`, `-0.0` and `1e-400`, and accepts `-0` as 0, as cliproxy-rs does. A refresh also refuses `"type":null` and `"thinking":{"levels":[null]}`, which Go serves as `"type":""` and `levels: [""]`. Model IDs are validated as Go decodes them. Go likewise keeps the previous catalog when no source decodes.
- Watcher startup: cliproxy-rs reads `config.yaml` once when the watcher starts, so an edit made after the config was loaded but before watching began takes effect. Go starts watching without rereading the file and keeps the older config until the next edit.
- Management JSON bodies: credential status, `/requests/api-call`, the OAuth callback `POST` and the Sign in with ChatGPT bind read the first JSON value and match member names the way gin's `ShouldBindJSON` does, and skip unknown members unread, as Go does. A member that names a string field and holds invalid UTF-8 or a lone surrogate escape (`"\ud800"`) answers that handler's invalid-body 400; Go binds it with U+FFFD in place of each bad byte or surrogate. `PATCH /credentials/fields` decodes its values as Go does, invalid text included. It refuses two kinds of value with 400 `invalid field <name>`: a number outside float64's range (`1e400`), and a value nested more than 127 levels deep, counting the file's root object and the objects a dotted field path creates, even around a scalar. Go writes both. It then cannot load the first kind (its float64 decode fails), and cliproxy-rs's auth loader cannot load the second.

- Usage records under Codex response steering (`codex.response-steering`): as in Go, each upstream response on the full-duplex socket gets its own usage record, published as soon as its terminal event, its own failure or, for a create upstream rejects before `response.created`, that rejection is observed, while the connection stays open. A record that settled is never changed by what happens later on the socket, and a duplicate terminal event adds no record. A message whose observation (an attached executor `WebSocketObserver`) is running when the client leaves still settles the record it names, undelivered; only the records it leaves open count as the client leaving. Four choices differ from Go. A failure event (`response.failed`, or `error`) that names an open or retained response, by `response.id` or `response_id`, settles that response's record even when a later response is running, leaves the later response running and leaves every create still waiting upstream in the queue; a failure naming a response that already settled settles nothing. Before any response history is evicted, an unmatched failure ID still rejects the oldest waiting create as inherited proxy policy from Go; first-party sources do not establish that FIFO ownership rule. The proxy retains settings for the 16 most recent starts and separately recognizes open records. Once history has been evicted, an unmatched ID could name an old settled response: the upstream frame is delivered unchanged and the socket ends with a local ambiguous-attribution failure, instead of declaring any pending create rejected by that upstream error. This also applies to a truly never-seen ID after eviction, because the two cannot be distinguished. A failure naming a retained settled ID settles nothing and leaves pending creates intact. A subsequent `response.created` reusing that ID starts a fresh record from its pending create; a failure alone cannot distinguish that reuse from the old response. Provider applicability of the unmatched-ID fallback remains unknown. When the inherited fallback ends the latest response with no pending create, only that response's still-open record fails. If the latest response already settled, the fallback adds no record and does not fail an older open response. A response still running, and a create sent upstream that has not started, when the connection ends: the client leaving records each as `context canceled` with status 499, the proxy's accounting convention from the entry above, and an upstream or connection failure records each as that failure. Go records only the response its reader is on, with the socket's or the client input's failure as a connection error, and only while the request context is live; once that context is canceled it records nothing, and it never records a create that did not start. A create's record starts when the proxy sends the create upstream, so its latency includes the wait for `response.created`; Go starts it at `response.created`. Its `ttft_ms` runs to the response's first upstream event (Go starts its TTFT clock at `response.created`), and it carries no `timings`, which measure the turn's own request; the first response keeps the turn's. An automatic successor takes the reasoning effort, service tier and model of the request whose settings it continues, as Go's does. Every record of the connection keeps the request ID of the turn whose dispatch carries the stream, and has its own execution ID. Frames the proxy refuses or holds in its queue never reach the upstream and get no record. A connection whose responses all settled publishes nothing more when it closes. The Codex contract defines no usage record. Apart from that failure association, which decides which create a later `response.created` serves (and so whether its metadata event precedes it) and whether queued creates wait for a running automatic successor, nothing here changes what reaches the client or the upstream, and credential health is unchanged. Before #25, the connection had one record: the first response's usage, published when the connection ended, or no tokens when it ended with an error.

- Responses WebSocket handshake metadata: when a turn served by a Codex credential with `websockets: true` opens a new upstream socket, the client receives `{"type":"response.metadata","headers":{...}}` before the turn's first event. It reads them from the upstream handshake when it connects directly, but this proxy sends its own 101 before the first request chooses the credential and the model. Backend applicability after a switch is unknown, so this policy can hide a still-applicable reroute notice. No other upstream header is carried. The event has the shape current Codex classifies (openai/codex `e0aa043`, `codex-api/src/endpoint/responses_websocket.rs` and `api_bridge.rs`): `{"type":"error","status":429,"error":{...},"headers":{...}}`. The error object is rebuilt from an allowlist: the type, a known quota code, a fixed message, and for `usage_limit_reached` a plan-like `plan_type`, `resets_at` (from `resets_in_seconds` when the upstream sent only that) and `limit_window_minutes`. `headers` keeps only `Retry-After` and Codex's rate-limit headers (the `x-codex-*` and active-limit window, limit-name, credit and reached-type headers), each checked against its expected value shape. - Codex context-window failures: when a Codex upstream answers `response.failed` with `response.error.code` `context_length_exceeded`, a Codex client (Codex or OpenAI Responses formats on both sides, and a Codex `User-Agent` or `originator` as in Go's `isCodexResponsesClientRequest`) receives that event unchanged. Current Codex classifies only this event as `ContextWindowExceeded`, then compacts the conversation and retries. The ChatGPT Codex backend rejects an input that alone exceeds the window differently, before `response.created`, with an `error` event that has no HTTP status: `{"type":"error","error":{"code":"context_length_exceeded",…},"response_id":…,"sequence_number":…}`. Codex ignores such an event, so a Codex client receives it rewritten as `{"type":"response.failed","sequence_number":…,"response":{"id":…,"object":"response","status":"failed","error":…}}`: `response.error` is the upstream `error` object byte for byte (code, message, type and param), `response.id` comes from `response_id`, and `sequence_number` is kept. On HTTP its SSE `event:` line becomes `response.failed` too. An `error` event with a positive `status` or `status_code` is Go's status frame, which Codex reads as an HTTP error, and it is unchanged. From here on, "the event" means either upstream event as the Codex client receives it. Go replaces the event with its classified error (`context_too_large`), which Codex treats as an invalid request: on the Responses WebSocket as a `{"type":"error","status":400}` event, and on HTTP as a `response.failed` with that code, or as an HTTP 400 when the failure is the first upstream event (with or without an SSE `event:` line before its data). Only the classified error that immediately follows the event is withheld; any other error or upstream close code, including one after a recoverable steering failure, reaches the client as in Go. The turn's classified error is taken before the event is written, and neither it nor an upstream socket that ends right after the event (without response steering) is reported as the session's loss: a slow client still gets the event, and a `response.interrupt` or a client that leaves during that write neither adds an interrupted `response.incomplete` nor turns the failure into a cancellation, so the client gets one terminal event and the scheduler one failure. In Go the disconnect watcher can close the client first with the socket's close error. On HTTP the stream ends with the event. This applies over a WebSocket upstream, with and without response steering, and over an HTTP upstream. The scheduler, the usage record and credential health see the same request-scoped error as in Go, and the credential is not cooled. A failure that is the first upstream event, over a WebSocket or over HTTP (with or without an SSE `event:` line), used to fail the stream's start; for a Codex client it now starts the stream with the event and is recorded as a failed stream rather than a failed stream start, so configured error rules (`request_scoped_errors`) do not run for it. Other clients, other failure codes, and an `error` event with this code that a response-steering socket receives after its first response are unchanged. On the Codex native WebSocket route (above), other clients also receive the upstream event unchanged, instead of Go's classified error.

- Compressed request bodies in request logs ([#101](https://github.com/zakstak/cliproxy-rs/issues/101)): the log's copy of a `zstd` request body is decoded with at most an 8 MiB window. - Codex Sign in with ChatGPT expiry: a JSON number in the `siwc` partition's expiry fields or in its access token's `exp` claim is read through serde_json's float parse, which can differ from Go's correctly rounded parse in the last bit for a value with more than 17 significant digits. - Sign in with ChatGPT binding ([#91](https://github.com/zakstak/cliproxy-rs/issues/91)): cliproxy-rs follows Go v8.0.67 instead of v8.0.35 in these points.

- Codex token renewal ([#92](https://github.com/zakstak/cliproxy-rs/issues/92)): refresh refusals follow the provider's sources, not Go v8.0.35's retries. Go v8.0.67 (`514d09f7`, `a96e640d`, `95f125ff`) moved the same way; its rotation relaxation and renewal-window enforcement are not ported.
  - Terminal refusals: the outer ChatGPT OAuth refresh is refused for good on HTTP 401, on `refresh_token_expired`, `refresh_token_reused` or `refresh_token_invalidated`, or on HTTP 400 with `invalid_grant`. This is first-party codex-rs at the contract pin (`request_chatgpt_token_refresh`). The Sign in with ChatGPT refresh is refused for good on the codes OpenAI's "SIWC errors and recovery" lists as an unusable refresh token: `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated` and `refresh_token_reused`. Such a token is sent once, not three times, and the same token fails at once for five minutes. Any other failure stays transient: retried, and backed off as before. Go v8.0.35 retries `invalid_grant` three times and stops only on `refresh_token_reused`.

Its token set (outer or SIWC) has no renewal credential until its refresh token changes, through a new sign-in, an upload, an edit or another process's rotation adopted from the file. Neither time nor a restart of the refresh loop lifts it; a process restart does, as the record lives in memory. The background refresh stops instead of retrying every 30 minutes. A due refresh, a refresh after an upstream 401 and a management refresh all skip the refused token set and still refresh the other one.

A credential whose active token was refused by an upstream 401, and whose refresh token has been refused for good, stays quarantined until that token set or `use_siwc` changes. Refreshing or replacing the other token set no longer lifts it, and neither does a manual refresh. The same applies to the 401 cooldown an upstream answer sets. A manual refresh of a credential whose active refresh token is refused saves what the other token set got, then answers 401 "sign in again". Go v8.0.35 lifts both on any token change.

  - With `use_siwc` off, a refused SIWC refresh token leaves the credential selectable on its outer tokens. Requests are never moved from SIWC to the outer tokens when SIWC is in use (OpenAI: no silent switch to another billing path).

Go clears only its unauthorized cooldowns and keeps a SIWC 403, 429 or 503 cooldown on the outer tokens. OpenAI's SIWC errors concern SIWC admission or a possibly app-specific usage limit, not the outer tokens (FP5, [#119](https://github.com/zakstak/cliproxy-rs/issues/119)). A SIWC binding still keeps the outer cooldowns other than unauthorized, as Go does.

The token set is the access token and the replacement refresh token: an answer without both is refused, nothing of it is applied, and the stored refresh token stays, as before. On a refresh, the endpoint has spent the stored token, so no other field discards a usable token set. A missing or unreadable `scope` keeps the stored grant (the refresh asks with none, which keeps it, and RFC 6749 §5.1 lets the answer omit it). A reported scope is stored as reported, even without `chatgpt.tokens.use.direct`. OpenAI's errors-and-recovery page says to retain such a sign-in and mark ChatGPT plan usage disabled. While `use_siwc` is on, requests on such a credential are refused before they are built, with a 403 that cools the credential and starts no refresh; the SIWC status reads `invalid`; the tokens keep renewing on their usual schedule. A stored grant without a scope is the bound one and stays usable. The code exchange of `--siwc-bind` and the Management API bind, which only add direct-inference credentials, still refuse a grant without that scope and write nothing. An `expires_in` that is not a positive JSON integer leaves the expiry unknown: the stored expiries are cleared (`null`), an explicit `null` `expired` stops any older expiry alias in the partition (`expire`, `expiresAt`, `expires_in`, a nested `token`) from being read, and the new access token's JWT `exp`, else `last_refresh`, schedules the next refresh. The integer parse is inherited from the earlier typed reader, not a provider rule; Go v8.0.67 (`09b3a579`) coerces `3600.0`, `3.6e3` and `"3600"` instead. Before, any of these refusals lost the replacement token and resent the spent one. An expiry whose year needs five digits cannot be stored as RFC 3339 and is unknown too; before, it was stored as "now", so the new token was due again at once. The code exchange keeps its strict reading. `earliest_refresh_at` is not read, persisted or enforced, because no source gives its format or meaning; Go v8.0.67 (`80ee739f`, `a46be7ae`) stores it and defers renewal until it.
  - A SIWC refresh answered with 200 but without a usable token set, or whose body could not be read or did not arrive within the attempt's 30 seconds, is not resent in the same refresh, because the endpoint may have spent the token. Go and the earlier version retried it twice more. It stays a transient failure, never a refusal, and a due refresh then waits for its five-minute backoff. The outer refresh keeps its own handling.
  - A due SIWC refresh that fails transiently is kept for five minutes as a backoff, as every outer failure is. When the token requests use was still valid, such a failure was tolerated and the scheduler checked again 30 seconds later, sending the same refresh token three more times each time. A refresh after an upstream 401 and a management refresh do not take a kept failure: they ask the endpoint again.
  - An outer refresh whose `expires_in` puts the expiry past what chrono can hold leaves `expired` empty, so the access token's JWT `exp` or `last_refresh` schedules the next refresh. Before, the refresh panicked and lost the rotated tokens. Go's `time.Duration` product wraps instead.
- `--siwc-bind`: the callback listener binds only the loopback address, which is the address in the redirect URI. Go listens on every interface. With a remote token store (PostgreSQL, Git or object storage), cliproxy-rs also saves the bound credential file to the store after a successful bind, and only that file. Go writes the bound file only into the local auth directory, so the next start from the store does not have the binding. The credential lock file (`<file>.lock`) is the same in both, so a Go or cliproxy-rs `--siwc-bind` waits for a Go refresh of that file. A cliproxy-rs refresh of a Codex credential file takes the same lock, from before it reads the file until it has written the result.
- Codex live request logs: in the logs of `POST /v1/live`, `POST /v1/realtime` and `POST /v1/realtime/calls`, the ICE credentials of SDP bodies (`a=ice-ufrag:` and `a=ice-pwd:` values, also inside JSON or multipart bodies) are written as `[REDACTED]`, in the downstream and upstream sections alike. Go logs those bodies unchanged. The bytes sent to the client and the upstream are not changed.
- `PUT /v0/management/config.yaml`: comment lines are unindented before the upload is checked, so the check sees the bytes that are written. Go checks the upload as sent and unindents while writing; when a `#` line sits inside a block scalar, Go can overwrite `config.yaml` with YAML that no longer loads and then answer `500 reload_failed`. cliproxy-rs answers `400 invalid_yaml` and leaves the file alone. Two answers differ from Go: a type mismatch such as `port: abc` is `422 invalid_config` (Go: `400 invalid_yaml`), and YAML syntax messages come from a different parser, so only the status and the error code match.
- Terminal UI (`-tui`):
  - Each reply goes to the tab that asked for it. Go hands replies to the active tab only, so a reply that arrives after a tab switch is lost (and an OAuth poll in progress never finishes).
  - While a text field has focus, every key except Ctrl+C goes to the field. Go still quits on `q`, switches language on `L` and changes tab on Tab while you type. On the password screen `q` and `L` keep their meaning while the field is empty.
  - The status bar sits on the last terminal row; Go leaves two empty rows under it.
  - Long lines are cut at the terminal edge: there is no horizontal scrolling (`h`/`l`). The cursor does not blink, and Ctrl+V does not read the system clipboard (a terminal paste works).
  - Adding a client API key sends `{"old": key, "new": key}`, which adds the key when it is missing. Go sends `{"old": null, "new": key}`, which its own server rejects with `400 missing fields`.
  - A delete or edit started on the Auth Files or API Keys tab acts on the item that was selected. Go resolves the list position again when you confirm, so a refresh in between can delete another file or change another key. API keys are addressed by position, so if a refresh moves the selected key the action is cancelled.
  - `-tui -management-base-url URL` is a pure client: it starts without a local config, store or Home bootstrap. Go loads them first, so it fails without a local config and waits in cloud mode.
  - `-tui -standalone` works without a management key in the config or `MANAGEMENT_PASSWORD`: its generated (or `-password`) password is accepted from loopback, also after a config reload. Go refuses every management request without a configured key, so its standalone TUI never connects then. The TUI connects to the address the server actually bound, so `port: 0` and IPv6 loopback work. A `server.tls` setup or a host that is neither loopback nor a wildcard address is refused with an error; in Go these fail after 30 connection attempts.
- `pprof`: the optional separate listener serves the index, `cmdline` and `symbol`, and CPU `profile` in builds with `--features cpa-server/pprof`. The profiler and symbol resolver dependencies are absent from default builds, published release binaries, the Docker image and CI's size-gate build. Profiles of the Go runtime (`heap`, `allocs`, `goroutine`, `block`, `mutex`, `threadcreate`, `trace`) have no Rust equivalent and answer `501` with a plain message; without the feature, `profile` answers `501` too and names the feature. Without the feature, `symbol` consumes POST bodies but returns only Go's `num_symbols: 1` header, with no resolved names, including shared-library names. With the feature, symbol lookup uses the symbols available in the executable, so an unstripped build gives more names. Symbol POST bodies and URL-encoded profile form bodies (POST, PUT and PATCH) are limited to the server's 64 MiB and a larger body gets `413`. Go reads symbol bodies without a limit and reads URL-encoded forms up to 10 MiB, ignoring a larger form so the query's `seconds` applies. Go's `FormValue` also reads `seconds` from a `multipart/form-data` body; cliproxy-rs reads only URL-encoded bodies, so a multipart `seconds` is ignored and the query applies. When a `Content-Type` repeats a parameter with conflicting values (`application/x-www-form-urlencoded; charset=a; charset=b`), Go's `mime.ParseMediaType` returns no media type, so Go ignores the body and uses the query's `seconds`. cliproxy-rs still reads the body. After an accept error that is not retried, connections already open keep running in both. The next config publication then gives them up to five seconds to finish before it binds the listener again, and after a timeout it waits for a further publication. Go discards the failed server, so its next publication binds without waiting for those connections. Listener addresses require numeric ports: unlike Go, `:` and service-name ports such as `:http` are not accepted.
- WebRTC media relay for Codex live calls (`oauth.providers.codex.live-media-relay`): every Go build includes it, and the config turns it on. In cliproxy-rs it is an optional build feature (`cargo build --release -p cliproxy --features cpa-server/media-relay`); the release binaries and the Docker image are built without it, so calls negotiate media directly with the upstream. In a build with the relay, TURN servers reached over TCP or TLS are skipped with a warning, because the WebRTC library cannot gather candidates through them; TURN over UDP and STUN work. Candidate gathering for the upstream peer stops after 6 seconds and the call goes on with the candidates gathered so far, because the library never finishes gathering when a STUN server stays silent. Go waits until gathering completes or the request is cancelled, so a TURN server that takes longer than 6 seconds to allocate a relay address still contributes a relay candidate in Go but not in cliproxy-rs.
- Images multipart forms: the `/v1/images/edits` route and the image executors read a form as Go's `ReadForm` reads it from an in-memory body, which takes a line of 4,096 bytes or more without a newline as `bufio: buffer full`. When Go's images route reads the request body directly (request logging off), the last read also reports the end of the body, so Go accepts a final boundary line of exactly 4,096 bytes that ends the body without a newline, or reports `multipart: NextPart: EOF` for another such line. cliproxy-rs refuses both with `multipart: NextPart: bufio: buffer full`.
- A base URL that Go's URL parser refuses (xAI WebSocket and Codex WebSocket routes, for example a percent-escaped host): both servers answer 500 with Go's parse error, cool the model for that credential, and start no retry round. Go does not count the attempt as having reached an upstream, because nothing was sent. cliproxy-rs counts it as one, since it marks every statusless error that way. This matters only when several credentials fail on the same request: Go then reports the last failure that did reach an upstream (for example another credential's 503), while cliproxy-rs may report the parse error if it came last. A base URL that Go's transport refuses, because it has no host (such as `https:relay.example`) or no `http` or `https` scheme (such as `relay.example`), counts as an upstream attempt in both. The xAI and Codex WebSocket routes refuse such a base URL themselves before dialing, as Go does, so there it is handled like a parse refusal.

- Codex responses without MIME: when a request asks for an HTTP event stream and the upstream omits Content-Type, inspect a bounded initial SSE framing prefix and replay it unchanged. This keeps native HTTP streaming, ChatGPT buffered aggregation and WebSocket HTTP fallback working with the observed ChatGPT backend. Explicit media types remain authoritative; a JSON aggregate still does not become a fabricated WebSocket event. See the Codex contract’s WebSocket HTTP fallback section.
